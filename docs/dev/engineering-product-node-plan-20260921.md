## 定调：进入完整产品闭环收敛期

建议将项目定位为：**面向个人开发者与少量可信用户、本地优先、能够执行实际工程任务并解释执行过程的 OpenClaw 桌面工作台。** 首版以 Windows x64、一个主要 provider、一类真实工程工作负载为收敛锚点；其他能力按实际支持范围逐步扩展。这是建议的交付边界，并非声称其他平台已不可用。

这与仓库已有方向相接：README 的首产品验证目标是 Windows x64 DCS Coding Controlled Preview；Runtime 收敛章程的用户价值是解释“模型收到什么、用户批准什么、实际发生什么、失败后怎样恢复”。用户此次进一步明确了取舍：需要产品出炉与完整工程证据，暂不需要大量用户、长期运营实验或严谨统计研究。

产品完整性以一条用户任务的完整生命周期衡量：从目标输入、执行、产物、验证，到失败处理、恢复和可追溯交付。架构完整性按这条链的需要收敛。上下文、记忆、工具、审批、编排、观测各模块的存在，尚不能单独证明整条链已经成立。

### 后续工作的价值顺序

1. **先让任务做完并能核对结果。** 工具调用、产物、真实测试、失败说明形成闭环。
2. **再让长任务能够安全中断与恢复。** 取消、批准、重启、重复请求不导致错写和重复副作用。
3. **再让过程可解释、可追溯。** 使用当前已有收据和日志能力，覆盖产品实际执行入口。
4. **最后以真实项目验证增强收益。** 上下文损失、定向再注入、成本优化和默认化用实际工作负载逐步证明。

这四项是价值优先级，不要求拆成四个新的架构大工程。

## 1. 建议采用的交付目标

交付一个少量用户可以实际使用的完整工程产品：可安装、可配置、核心任务能从 UI 执行到底、失败可解释、重启可恢复、变更可回退、证据可追溯。真人长期记录和统计显著性不再作为首版交付的共同前置。

具体调整是降低观察周期、支持面和重复验证成本，保留发布范围内的功能正确性、审批与写入边界、恢复语义、证据真实性。工程交付完成、某功能允许开启、用户长期认可分别记录；某个研究结论为负面，可以关闭研究任务，但不能自动放行相应功能。

3. **签发本节点的有限结论。** 记录 scope、candidate/base、gate 列表、日志和输出摘要；通过后只解锁 TF-0030。完整 UI 套件、发行资源与发布签名/来源校验交给 TF-0041，在正式首版交付前仍须满足其适用门禁。

门禁分层必须先同步 Harness task/rule、acceptance profile 和校验器，再生成新 manifest；旧 NO-GO 原样保留。不能只在命令行删门、调大 timeout、改 skip 数或重新签旧产物。

日常反馈改为“便宜预检 → 失败项及相关回归 → 当前包闭合 → 最终冻结候选全量复验”。同一候选通过后不无理由重复；候选或相关输入变化则按影响范围重新验证，最终交付仍绑定同一可复现版本。

## 5. 压缩观察周期的具体方案

建议首轮采用以下工程筛选值；这是待落地的验收设计，不是已取得的成绩或长期可靠性承诺。

| 阶段 | 投入与覆盖 | 判定 |
| --- | --- | --- |
| 验证链路 | 30–60 分钟；启动 ClawX、真实 provider 回复、一个工作区任务、检查实际文件/日志/收据 | 任一关键环节不通就先修，避免提前启动长跑 |
| 工程场景集 | 约 2–4 小时目标窗口；12 条代表性旅程各 3 次，合计约 36 条。已有匹配当前候选的同范围场景可复用，不重复凑数 | 发布范围内的关键旅程与不变量全部通过，失败尝试与重试完整保留 |
| 累积与恢复 | 至少 3 批，跨应用/Gateway 重启；复用同一验收数据目录，观察清理、重连和累积状态 | 报告真实 elapsed duration，持久化与恢复断言通过；多 seed 不冒充多天 |
| 24 小时观察 | 在设备条件允许时补充，首版后继续积累 | 初始缺少该观察可作为已知限制；已发现的严重缺陷仍须处理 |
| 14 天真人记录 | 产品出炉后自然沉淀 | 用于增强长期结论，不反向阻塞已经定义清楚的首版工程交付 |

建议 12 条旅程围绕实际产品：首次启动/配置、正常编码任务、文件改动与测试、工具失败后恢复、长会话压缩、取消执行、拒绝审批、重复审批、pending 时重启、effect 完成后重启、fork/handoff、功能开关与恢复。与 H-01..H-06 对齐，按首版范围补入 DCS/SEKB/Browser 子路径；真实 channel 若承诺支持则必须有实际适配器往返。

执行链应为：

```text
CDP / Playwright 操作 ClawX Electron UI
  → Main / host-api → Gateway → OpenClaw → 选定 provider / 实际工具
  → 一次性验收工作区里的真实结果
  → UI 结果 + run/receipt/effect/实际文件校验
```

可以模拟操作者和故障，依赖与外部效果按场景标注真实或替身。仅测试页面 fixture 的结果归 UI 验证；仅直接调用 moyu API 的结果归测试工具验证。CDP 能操作 Electron renderer，但跨进程重启、持久化与真实执行还需 Electron 主进程/Gateway 测试支持，不能靠截图独立证明。

前期使用临时小项目或现有 moyu 项目作为工作负载即可，收到完整项目后替换输入；保留相同场景标识和证据格式，无需再建一套系统。扩展现有 E2E fixture、scenario registry 与 surrogate 收集器，避免新增 planner、常驻 daemon 或第二任务真源。

最小证据字段：场景与验收标准版本、候选 commit/build digest、实际 flags、operator 类型、provider/依赖类型、workspace 输入摘要、开始/结束与真实时长、run/request/receipt IDs、关键步骤、预期与实际输出、日志/文件摘要、失败与重试、恢复/回滚结果。UI trace/截图辅助解释，副作用正确性由实际结果断言支持。敏感原始数据留在受控本地目录，分享脱敏摘要与哈希。

长时 soak 和时钟推进测试分开记录：后者可测 TTL/过期边界，不能证明真实 14 天稳定性。与安全相关的审批拒绝、重复 effect、越权写入和恢复不丢状态，要求零违反；不以总体平均 pass rate 抵消。
