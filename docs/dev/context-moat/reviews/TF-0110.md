## 关键语义决定（req-4 的选择 + AC-3/req-5 的调和，均写明理由）

**决定 1（req-4，选 (b)「真实路径也禁止」）**：`secret_adjacent` 由门控禁止（既有行为），并在 use gate 被咨询时同样被真实注入路径禁止——通过 `applyMemoryUseGateOverlay` 在两条生产注入路径上实现。两侧从此一致。选择理由：(a) 侧（门控放行 + 保留 redact）不成立——仓内不存在针对 `secret_adjacent` 的 redact 机制，无可保留；且节点 summary 明指「`secret_adjacent` 反被 `bucketForMemory` 归入 hardConstraints 最高优先级桶」是缺陷本身，放行方向与治理意图相反。gate 关闭时真实路径保持旧行为（AC-1 明文要求「关闭时行为与改动前一致」），分级不一致仅在门控关闭的过渡态残留，这是 P3-003 分阶段上线的既定代价。

**决定 2（write gate 的咨询条件）**：`proposeMemoryCard` 在「门被显式配置」（调用方传 `options.dualGate` 或 env `OPENCLAW_MEMORY_WRITE_GATE` 已设）时咨询 `evaluateMemoryWriteGate`；未配置的调用方保持旧提案流。理由：AC-3 要求 `writeEnabled=false` 时拒绝并给出明确 reason（实测按默认解析拒绝会使仓内 6 个既有套件、几十条依赖 `proposeMemoryCard` 默认受理的用例全部破坏——实测 `tests/unit` 下 6 个调用文件 32 用例，默认拒绝方案逐一验证会红，违反 §D4.6 回归定义）；显式配置咨询同时满足 AC-3（测试以显式 `dualGate` 触发拒绝）与 req-5（默认行为逐字节不变）。代价：未显式配置的生产调用方（gateway RPC `memory.propose`、mission-control 自动提案）在默认态仍不咨询 write gate——这是 F5 缺陷的**部分修复**，完整治理需要上游调用方携带门控配置或另立任务统一打开，已记入三分类。

**决定 3（use gate 的 overlay 语义）**：生产注入路径把 use gate 作为「启用即严格过滤」的叠加层：`useEnabled=true` → `evaluateMemoryUseGate` 过滤（去 secret/secret_adjacent/poison/tombstone）；`useEnabled=false`（默认）→ 原样透传，与改动前一致（AC-1）。`simulateMemoryInjection` 保持「启用契约直模」（门关 = 不可注入）不变，两者语义差异已在 `memory-dual-gate.ts` 模块头注释如实写明。
