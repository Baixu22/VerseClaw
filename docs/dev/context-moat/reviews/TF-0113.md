### req-1：挂 `transport.onclose` / `onerror`

三个实现细节都不是随手选的：

1. **必须挂在 `connectWithTimeout` 成功之后**，不能挂在 session 建立时。SDK 的 `Protocol.connect()` 自己会赋值 `transport.onclose` / `onerror`；挂早了会被它覆盖，等于没挂。
2. **必须链式调用而非替换**：先存下 SDK 装的 handler 再调用它，否则会吃掉 SDK 自身的 teardown。
3. **只在 `!connected` 分支内挂**，故 session 被复用时不会重复挂钩。

### req-2：per-server 粒度

`catalog` 是**单个** memo，任何失效都会清空它 —— 但这不等于丢掉其他 server 的工具。关键在于只把断连的那个 server 从 `sessions` 里删掉：重建时其余 server 走 `reusedSession` 路径**跳过 `connectWithTimeout`**，直接重发 `tools/list`。故单个死 server 不会放大成全体重握手。

第二条测试用一个**服务端连接计数器**把这条断言机械化：alpha 断连后重建，`beta.connectCount()` 仍为 `1`。若哪天有人把失效改成清空 `sessions`，这条会红。

### req-3：`list_changed` 与 `dispose` 行为不变

把 `onChanged` 里内联的三行（`generation += 1` / `catalog = null` / `catalogInFlight = undefined`）抽成 `invalidateCatalogMemo()` 并改为调用它 —— **逐字节等价**，且让失效不变量有了单一真相源。第三条测试（新增工具后 `list_changed` 触发重建、`connectCount` 仍为 1）是这条重构的回归守卫。`dispose` 路径未触碰；第四条测试断言 dispose 之后迟到的 close 事件是 no-op，不会在已废弃的 runtime 上复活状态。

### 一处上报的偏差：`onerror` 收窄

`requirement-1` 字面要求两个信号做同一件事（含「摘除 session」）。实现对 `onerror` **只 invalidate、不摘除**。

理由：transport 对**可恢复**错误同样 fire `onerror`（SSE/streamable-http 的瞬时网络错误、stdio 的畸形消息）。而摘除 session 会连带 `disposeSession` —— 对 stdio 传输那意味着**杀掉一个仍在运行的子进程**。按字面实现会在一次瞬时错误上摧毁健康服务器，等于用一个更严重的故障替换掉本 task 要修的故障。

模型可见面的结果不变，这是本项不算功能缺失的依据：`onerror` 后 memo 被清 → 下一次 `getCatalog` 在保留的 session 上重发 `tools/list` → 若服务器确实已死则抛错并被既有的 per-server catch（`:743-762`）降级进 diagnostics → 该 server 的工具同样从声明面消失。差别只是「已死 session 多存活一个重建周期」，而那是本改动**之前就有**的行为（`reusedSession` 路径从不删 session），不是新引入的退步。

按 §R5 范围-2，实施者无权自判这算不算降级。已记 `TFD-lane2-tf0113-onerror-narrowing-2026-08-27`（`open`），三个出路写在其 `recommendation` 里，**裁决权在 lane-1**。

### AC-3：既有熔断机制已定位

节点原文写「既往报告提到 3 次失败 60s 熔断，本轮未定位到坐标，须在实施时确认或否证」。**确认存在**：

agent-bundle-mcp-runtime.ts:60   BUNDLE_MCP_FAILURE_COOLDOWN_MS = 60_000

**与本改动的交互：无冲突，但覆盖面不重叠。** 五个 `runGuardedServerRequest` 调用点（`:904` / `:924` / `:935` / `:948` / `:959`）全是 per-server 请求方法（`callTool` / `listResources` / `readResource` 等）；catalog 重建路径直接调 `listAllToolsBestEffort`，**不经过该守卫**。即熔断器保护工具调用、不保护目录重建。

这对本改动不构成风险：一个死掉的 transport 只 fire 一次 `onclose`，且重建失败后 `catalog` 仍被 memo（错误落进 diagnostics），故不会出现「每次 `getCatalog` 都重连死服务器」的风暴。**如实登记这处不重叠，不声称熔断器覆盖了新路径。**

### 附带修好的第二半（不在 requirements 内）

`callTool`（`:896-902`）的形态是 `await getCatalog()` → `sessions.get(serverName)` → 无则抛 `bundle-mcp server "X" is not connected`。改动前 session 永不因断连被摘除，所以 node summary 描述的「`callTool` 命中缓存立即返回，调用打到已死 client」成立；改动后 `close` 会摘除 session，同一条 `callTool` 转为**快速失败并给出明确错误**。即 requirement-1 的「摘除 session」不只让目录正确，它同时关掉了 `callTool` 那条路径。

### 裁决 (1)：`onerror` 收窄 —— 接受，走出路 (a)，但理由须改写

**接受收窄。** 我独立验证了那条附带损害是真的：`disposeSession`（`:406-`）会调 `session.transport.close()`，而 SDK 的 `StdioClientTransport.close()`（`dist/esm/client/stdio.js:137+`）会 `stdin.end()` 并等子进程 `close` 事件 —— 对 stdio 传输，那就是**杀掉一个仍在运行的子进程**。req-1 的字面要求在可恢复错误上会把一次可恢复故障换成一次不可恢复故障，这不是实现偷懒，是字面要求本身有害。故 `TFD-lane2-tf0113-onerror-narrowing-2026-08-27` 判为**合法偏差**，取出路 (a)：改写 req-1 措辞，把 `onclose` 与 `onerror` 的职责分开写明。

**但收窄的理由必须改写，现在这版把等价性说过头了。** lane-2 写的是「if the server really is gone the list throws and the existing per-server catch drops its tools into diagnostics, which is the **same** model-visible outcome without the collateral」。目录面确实等价，**session 面不等价**：重建路径的清理是 `if (!reusedSession)` 门控的（`:825-828`），而 `onerror`-only 失效之后 session 恰恰**是**被复用的，所以

- 死 session 会无限期留在 `sessions` 里，每次重建都对它重发一次 `tools/list` 并各吃一次超时；
- `callTool` 取得到 session，于是仍然打到已死 client，靠 3 次/60s 熔断器兜底，而不是 `not connected` 快速失败 —— **这正是 node summary 描述的原始缺陷形态**。

触发条件很窄（需要「真死」却只 fire `onerror` 不 fire `onclose`），实践中 stdio 子进程死亡与 socket 断开都会 fire `onclose`，所以我不判它阻塞。但它必须写成残留而不是写成等价。
