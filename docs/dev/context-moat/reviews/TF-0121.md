## 规范冲突与 risk 裁决

### 事实

`harness/specs/rules/context-family-boundary.md:59-60` 规定 read-only recall 不得写 Memory、Knowledge、Task Ledger、transcript、prompt state、workspace files、approvals 或 tool state。`harness/specs/tasks/context-readonly-recall-surface.md:15-40` 同样要求 recall 不写 durable state，且 mutation 必须走单独 reviewed workflow。

TF-0121 的公开面是：

- 工具名：`context_read`
- 参数：`include_archived=true`
- 行为：archived → active，heat +1，持久化 `presence_json`
- 元数据：`risk: "readonly"`

`tool-registration.ts:66-75` 明确 `readonly/write/destructive` 是 filesystem write enforcement 分类；`writeRiskProfile` 也只描述文件写入路径。

### 裁决

1. **技术边界：接受“独立 DCS BlockStore lifecycle page-in”解释。** 默认 `context_read` 不写；显式 opt-in 才进入 BlockStore authority 内的 lifecycle 写事务。它不是 Context Family ArchiveHandle recall。
2. **公开契约：不接受直接关闭冲突。** `context_read` 名称 + `include_archived` 参数会让使用者合理期待 read-only；当前枚举又无法表达“条件性 durable mutation”。这不是实现者可单方面用注释消掉的歧义。
3. **最小诚实方案：保留 `risk: "readonly"`，但不得把它解释为“无 durable mutation”。** 改成 `write` 会错误声明 filesystem 写入并强制不匹配的 `writeRiskProfile`；当前枚举没有更准确值。
4. **后续必须拆分或修规范：** 要么把 lifecycle page-in 拆成独立工具/参数面（例如 `context_recall_archived`），保留 `context_read` 严格只读；要么修订 Context Family/DCS 规范并扩展风险模型，显式授权 conditional BlockStore lifecycle mutation。二者选一，落成后续 task/spec，不能靠口头解释收口。

因此，规范冲突是 **blocking governance gap**，不是“实现绿了所以忽略”的备注。
