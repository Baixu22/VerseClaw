## 三点发现

### 发现 1（backlog-P1）—— §R5 同时声明「不为第二轮预设边界」又预设了一条

§R5 末句：「也**不为第二轮预设边界**」。
但技术-5 的【补充】：「若**第二轮**触碰 `src/state/*`，迁移限定 additive-only 并过 `sqlite-schema-shape` 守卫。」—— 这**正是**一条第二轮边界。

**归因（重要）**：矛盾**源自节点自身**，不是实现者引入的。我核了节点原文：

- `requirements[4]`（技术-5）确含「若第二轮触碰 src/state/*，迁移限定 additive-only …」
- `non_goals[1]` 确为「不为第二轮预设边界」

### 发现 3（backlog-P1；但这是本次审核最有价值的一条）—— 「有执行器」与「生产可达」是两个不同谓词，§D1.2 脚本无法用于 A4 的执行器检查

§R5 过程-9 的判例是 `worktree.backend`「有叶子无执行器」。我复算**确认该判例成立**，但发现更精确的形态，且它暴露一处协议缺口：

| 事实 | 证据 |
|---|---|
| 存在**能够**按 backend 分支的实现 | `worktree-service.ts:160-162`：`if (requested !== "git") return "inprocess"; return isGitRepo(baseRoot) ? "git" : "inprocess"` |
| 但它读的**不是**旗标 | `worktree-service.ts:267`：`const requested = options?.backend ?? "inprocess"` —— 来自**函数入参** |
| 旗标解析器的**唯一**生产消费者是上报 | `resolveWorktreeBackend(cfg)` 仅被 `runtime-flag-ack.ts:272` 消费，写进 `codingFlat` **上报映射**；无行为切换 |
| 而该旗标在 §D1.2 脚本下判**可达** | `node …/check-production-reachable.mjs resolveWorktreeBackend` → `PRODUCTION REACHABLE`，**exit 0** |

**所以精确表述是**：执行器**存在**，但与旗标**未接线** —— 旗标被解析、被上报，其值从不流向会据此分支的代码。这比「无执行器」更准，也直接收窄我后续 TF-0137 的两条合法出口：修法不是「写一个执行器」（已有），而是「把旗标接到 `options.backend`」或「下架旗标」。

**协议缺口**：§R5 过程-9 规定「声明『旗标关闭』为回滚方式时，**A1 审核**必须同时验证该旗标存在执行器」。而 A1 的取证工具是 §D1.2 脚本 —— 该脚本判的是**可达性**，不是**执行器性**。`worktree.backend` 即活体反例：脚本给 exit 0，而它恰恰是过程-9 的「无执行器」判例本身。

⟹ **只用 §D1.2 脚本满足 A4 第五面（执行器）会得到假 PASS。** §R5 文本本身没说脚本能做这件事（它写的是「A1 审核必须验证」），故不判 §R5 有缺陷；但建议 §R1 的 A4 格加一句：执行器检查须追至**行为分支点**，且确认旗标值真的流到该分支点，不得以「脚本 exit 0」代替。归 **backlog-P1**，路由至 §R1（车道 1）与我的 **TF-0137**。
