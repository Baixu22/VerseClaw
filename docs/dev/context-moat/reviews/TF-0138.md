## 3. 发现与三分类

**阻塞本任务 0 / backlog-P1 3 / 升级-P0-需人工批准 0。**

### 发现 1（backlog-P1）：Q3 字段清单漏了 `droppedMessagesList` 的孤儿消息缺口

这一条落在 spike 声称「可精确定位到单元级」的**那一类里面**，所以值得单独记。

`compaction-planning.ts:330-362` 实测：

```text
droppedMessages  += dropped.length + orphanedCount        // 计数含孤儿
allDroppedMessages.push(...dropped)                        // 单元列表不含孤儿
```

`:357-360` 的注释自己写明了原因与其适用边界：

> Note: We don't have the actual orphaned messages to add to droppedMessagesList
> since repairToolUseResultPairing doesn't return them. This is acceptable since
> the dropped messages are used for summarization, and orphaned tool_results
> without their tool_use context aren't useful for summarization anyway.

**「对摘要无用」不等于「对损失归因无用」。** 一条被丢的孤儿 `tool_result` 恰恰是一个丢失单元；聚合计数说丢了 N 条、单元列表只给出 N − orphanedCount 条，两个数字对不上而没有任何地方解释差额。

为什么这不影响本 spike 的读数：spike 走的是**会话 JSONL 的位置边界**重建被丢集合（234 = 边界前全部 message），而不是读 `droppedMessagesList`。这条路径上重建是完整的。**但它直接影响 T-C2**：若 T-C2 选择在 planning 站点记录 per-unit 丢弃（那正是唯一知道 reason 的地方），就会系统性漏掉 `orphanedCount` 个单元，且漏掉的量不可从落盘数据反推。

处置：作为第十条字段/约束追加进 TF-0129（本次裁决一并落地），不退回 TF-0138 —— spike 的测量没有错，是字段清单的覆盖面差一项。

### 发现 2（backlog-P1，已在本次裁决中修掉）：TF-0129 requirement-6 与 AC-1 自相矛盾

新增的 requirement-6 写着「现 AC-1 ⋯ 在当前事实下不可达 ⋯ **改为**『≥3 类各有单测归类证据 ＋ ≥1 类有真实会话证据』」，但 TF-0129 的 `acceptance_criteria[1]` 原文**未改**，仍是「对一个 ≥40 轮 + ≥2 次压缩的真实会话 JSONL，能产出损失追踪并列出至少三类不同丢弃决策」。

于是节点同时带着：一条**已被实测证明不可满足**的 AC（≥2 次压缩的语料不存在，且只有 1 类有实例），和一条要求替换它的 requirement。接手 round-2 的人按 AC 验收会被一个不可达判据挡住，按 requirement 验收又找不到 AC 的授权 —— 这与 `XL-004` 报的「约束挂在没人会读的地方」是同一族失效，只是这次是「两份互相矛盾的判据都在原地」。

处置：**本次裁决直接把 AC-1 改写为 requirement-6 命令的解耦形式**，不留给下一个人。理由与 XL-004 同：一个自相矛盾的判据留在图里，等价于没有判据。

### 发现 3（backlog-P1）：脱敏自检 fail-open —— 先落盘再退出 1

`context-loss-trace-spike.mjs` 的执行顺序（`main()`，行号取自当前 HEAD）：

```text
471  const leaks = desensitisationCheck(...)      // 先检查
485  if (outPath) writeFileSync(...)              // 再无条件写盘
527  process.exit(leaks.length > 0 ? 1 : 0)       // 最后才按结果退出
```

即：**发现泄漏时，带泄漏的报告已经写到磁盘上了**，退出码 1 只是事后告警。自检的全部意义是阻止泄漏物落盘，当前实现只做到「落盘后告知」。

严重度按 backlog-P1 而非阻塞的理由：本轮该报告刻意不入库（文档 §8 明写「一条命令即可重现，入库只会给半径再加一个路径」，我认可这个取舍），且脚本是一次性 spike 工具、非生产路径。但若 T-C2 复用这段自检逻辑，就必须改成**先检查后写**（或写临时文件、检查通过再落定）。

变异抽查确认自检真的有拦截能力（不是永不报警的空守卫）：把 `LEAK_PATTERNS` 的 `session-uuid` 模式临时改为匹配 `ref:` 前缀后复跑，findings 由 0 变为 1 且退出码转 1；随即按字节还原，`git diff HEAD -- scripts/context-loss-trace-spike.mjs` 为空。

## 4. 对 XL-007 五个请求项的逐条答复

### (1) 三问答案与五类可观测性判定 —— **成立**，附一处精度更正

「一、否、六」在我的独立复测下逐条对上（§1.2/§1.3/§1.4）。五类的逐类载体位置我按代码核对过（§1.4 表格），四个「NO」的判定依据各不相同且都准确：

- `budget-drop` / `skipChannels`：语义存在（九值枚举）但载体在内存，`collections.delete` 抹掉；落盘载体 0 行 —— 判 NO 正确。
- `limitHistoryTurns`：`history.ts:20-41` 确认是纯 `slice`，无记录点 —— 判 NO 正确，且「与从未存在不可区分」这句措辞精确。
- `archived`：16 行 block 全部无 `lifecycle_state` —— 判 NO 正确，且性质是「结构上零实例」而非「暂时未观测」，这个区分很重要，我的 TF-0121 测量独立支持它。

**一处精度更正：** stdout 的 `units carrying a reason = 0` 是**构造出来的常量**，不是测量值 —— `traceCompactions` 在 `:213` 把每个单元的 `reason` 硬编码为 `null`，`report.q1_locatable.unitsWithReason` 在 `:457` 硬编码为 `0`。今天这个 0 在事实上是对的（该载体确实没有 per-unit reason 字段），但它是**同义反复而非度量**：若将来某个源真的携带 reason，这个字段仍会报 0。文档 §3 表格把「定位到原因的单元数 0 / 234」列在「实测值」一栏，措辞上把重言当成了观测。

不改判 PASS 的理由：文档同一节以及 Q2 表格都另外用「无 per-unit reason」正面陈述了这个事实，读者不会被误导到错误结论；且这属于指标构造的精度问题，不影响任何下游裁决。**但 T-C2 若沿用该字段名做「携带原因的单元比例」指标，必须改成真实推导。**

### (2) 六组字段清单 —— **不完备**，缺一项

六组本身都成立，其中「三组是搬运已有值」这个判断我核对过并认可：`reason` 的九值枚举（`context-candidate.ts:31-40`）确实与追踪所需一字不差，`charsRequested` / `charsApplied` 确实已在 lineage 与 `ReceiptBudget` 里。**这条对 T-C2 估价的修正比字段清单本身更有价值** —— 它把「设计新语义」降级为「加持久化」。

「两源不可 join」是清单里最硬的一条，我独立确认：`runtime_receipts` 的 23 列按 `attempt_index` / `model_call_index` / `wire_attempt_index` 键控，而会话 JSONL entry 上没有任何轮次身份字段。这不是补一个字段能解决的，是两个数据模型没有公共键。

**缺的第七项：** `droppedMessagesList` 的孤儿消息缺口（§3 发现 1）。它必须进清单，因为它落在唯一可观测的那一类里 —— spike 说「compaction 一类可以精确定位到单元级」，而在 planning 站点这句话有一个已知的、量级未记录的例外。

### (4) 语料口径 —— **接受为 requirement-2 的合法满足方式**

判定：**接受**，理由三条，按强度排列。

1. **requirement-2 是硬约束，node summary 不是。** requirement-2 说「必须使用真实会话数据，不得用合成语料（否则 spike 结论无效）」。`≥2 次压缩` 只出现在 `summary` 与 `execution_hints` 里。当两者冲突时，合成一份两次压缩的语料会**直接违反**唯一的硬约束，而在单次压缩的真实语料上执行只是**未覆盖**部分结论。前者让结论无效，后者让结论有边界。
2. **该语料被证明不存在，不是没找到。** TF-0143 实测 174 个会话压缩次数上限恒为 1。**我在裁决 `XL-009` 时对这个数做了独立重算**（同一会话内的后续步骤，非 XL-005 当时）：174 个非 trajectory 会话，压缩次数直方图 `{0: 163, 1: 11}`，全语料上限 **1**，满足 `≥40 轮 且 ≥2 次压缩` 者 **0** 个；11 个有压缩的会话里只有一个达到 41 轮，正是本 spike 用的那一个。继续等不是「等一个稀有样本」，而是等一个必须靠真实续跑现造的事件，且续跑依赖当前不可用的外部模型凭据。以 `≥2` 为收口前置等于把 spike 无限期挂起。
3. **受限结论被逐条标注，没有越界声称。** 文档 §9 点名三条未验证结论（跨轮摘要合并、多次压缩的 boundary 链、损失叠加），并说明其余结论不依赖压缩次数。我核对了这个划分：五类可观测性、字段清单、`runtime_receipts` 0 行、`archived` 零实例、两源不可 join —— 全部只依赖单次快照与代码结构，与压缩次数无关。**划分正确。**

**附加义务（收口条件的一部分）：** 三条未验证结论不得在 round-2 被当作已验证引用。requirement-7 已把 `archived` 那条的前向义务写进 TF-0129；另两条（跨轮摘要合并、损失叠加）属 TF-0111 与 T-C2 的交叉面，本裁决要求在 TF-0129 的 evidence 中登记「这三条来自单次压缩语料，未验证」，避免下一轮把 spike 当全量结论引用。
