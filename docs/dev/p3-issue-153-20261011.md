## Root cause

`harness/src/cli.mjs` routes a spec through `validateGatewayTaskSpec` whenever
`isGatewayBackendCommunicationTask(spec)` is true, and that predicate keyed only
off the frontmatter:

```js
export function isGatewayBackendCommunicationTask(spec) {
  return spec.data?.scenario === 'gateway-backend-communication'
    || toArray(spec.data?.scenarios).includes('gateway-backend-communication');
}
```

`scenario:`/`scenarios:` is scenario-applicability metadata. Rule, guide and
layer specs carry it (or the equivalent `appliesTo:`) to declare which
registered scenario they belong to. It is not a task declaration. This rule spec
was the only checked-in spec that combined a non-task `type` with a `scenario:`
key, so it was misclassified as a task and forced through task-only validation.

Task identity comes from the spec location (`harness/specs/tasks/`), which is how
the library already loads and separates scenarios, rules, guides and layers
(`loadScenarioSpecs`, `loadRuleSpecs`, `loadGuideSpecs`, `loadLayerSpecs`).

## Fix

- `harness/src/specs.mjs` adds `isTaskSpec(spec)`: true only for specs under
  `harness/specs/tasks/`. Pathless unit fixtures keep the legacy behaviour unless
  they declare a non-task `type`. `isGatewayBackendCommunicationTask` and
  `isPluginLifecycleTask` now return false for non-task specs.
- `harness/specs/rules/dcs-stage5-sekb-closure-boundary.md` drops the vestigial
  `scenario:` key, which only restated its `appliesTo` entry.
- `harness/src/specs.d.mts` gains the `isTaskSpec` typing-surface export.
- `tests/unit/harness-specs.test.ts` adds three regression tests.

The issue's two suggested directions (pad the rule spec with task-only fields,
or move it out of `rules/` and unwind its task-spec references) were rejected as
symptom fixes: both would keep the classifier able to misroute any future
non-task spec that carries scenario metadata.
