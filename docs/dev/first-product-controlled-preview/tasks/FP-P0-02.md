## Goal（用户可见结果）
运维把配置型 kill（`runtime.contextEnhancement.killSwitch=true`）打开后，**所有** context 增强注入路径立刻停止，包括 working-memory；不需要改 env、不需要重启。

## Why this exists
`Assembler.assemble()` 调用 kill 判定时不传 runtime config：
- `openclaw_runtime/src/context-engine/assembler.ts:138` → `isContextEnhancementKillSwitchEngaged()` 无参数
- 判定函数签名支持 `cfg`：`openclaw_runtime/src/context-engine/enhancement-kill-switch.ts:52-64`

于是只有 env kill 有效，配置型 kill 在这条路径上是**空开关**。首发承诺「kill/rollback 可解释」，空开关直接推翻该承诺。

## Non-goals
- 不重构 Assembler 结构
- 不新增 kill 来源或改优先级语义
- 不动 CVK 双投影问题（→ `FP-P0-05`）

## 实现要点
1. `AssembleRequest` 或 `AssemblerDependencies` 增加 cfg 通道（倾向 request 级，避免构造期快照过期）。
2. 逐个调用点补传 cfg —— **必须穷举**，遗漏点等于空开关残留。
3. working-memory 注入路径同样受 kill 覆盖（含 BlockStore 查询与注入两段）。
4. cfg 不可用时 fail-closed（保持现有 catch 语义）。

### 为什么调用点 1 不传 cfg（关键裁定）

任务书要求「cfg 走 request 级而非构造期快照，避免过期」。`buildWorkingMemoryFactory` 只持有
**agent 启动时**的 `params.cfg` 快照 —— 把它传进去恰好制造了任务书禁止的过期快照：运维在会话
中途打开配置 kill 时，该快照仍是 `killSwitch: false`，kill 依然切不断。

因此实现改为：**调用点不传 cfg**，由 `assemble()` 通过
`resolveAssembleKillSwitchConfig()`（`assembler.ts:127`）在**每次 assemble 时**解析。
`request.cfg` 仍保留为显式覆盖通道（测试与已持有新鲜 cfg 的调用方使用）。
按 mtime+size 戳缓存（`kill-switch-config-source.ts`），配置一写即失效，避免每 turn 读盘。

## 途中发现的更严重缺陷（已修）

任务书判断配置型 kill 是「空开关」。实测更糟：**它根本无法写入**。
`runtime.contextEnhancement` 存在于 `types.openclaw.ts:284` 且被 kill 判定读取、
`schema.labels.ts:779` / `schema.help.ts:2079` 都有条目，但 **`zod-schema.ts` 的 strict
schema 里没有这个叶子**。写入该配置 → 校验失败 → gateway child 以 `code=1` 退出、根本起不来。

发现路径：FP-P0-02 的 G3 E2E 首跑失败，报
`Gateway process exited before becoming ready (code=1)`。若只做单测（传对象进函数）
永远发现不了这个缺陷 —— 这正是 G3 要求真 child 的价值。已在 `zod-schema.ts` 补齐并实测
gateway 正常启动、kill 生效。
