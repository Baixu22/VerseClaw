## Goal（用户可见结果）
FP-P0 的 GO 结论有一个**非实现人**背书，而不是实现人自己签的字。

## Why this exists
`FP-P0-01…05` 与阶段出口验收均由同一人（Claude）完成，DoD G5 的
「验收人 ≠ 实现人」未满足，按允许的 self-accept 路径处理并留了代偿
（验收人重跑全部命令、反向注入验证守卫、问题只转不改）。

代偿降低但**未消除**同一人既写实现又定验收标准的盲区风险 —— 典型盲区是
「断言写得刚好覆盖自己实现的路径」，自己复核时不易发现。

## Non-goals
- 不重做 FP-P0 的实现
- 不重新裁定 FP-P0-01 / FP-P0-05 的 Decision（除非发现事实错误）
- 不扩大 FP-P0 范围

## 复核清单（复核人执行）
1. **独立重跑**出口验收里列出的全部命令，比对计数。
2. **抽查断言强度**：至少挑 3 条 AC，尝试构造一个「实现有 bug 但断言仍绿」的场景。
   重点怀疑对象：
   - `tests/unit/vtoken-launch-default.test.ts` 的源码级守卫（正则是否可被绕过）
   - `tests/unit/launch-contract-matrix.test.ts` 的 resolver 侧断言（是否真的读了 child 语义）
   - `electron/services/dcs-flag-ack.ts` 的超时分支（时钟注入是否掩盖了真实竞态）
3. **复核 FP-P0-02 的关键裁定**：「调用点不传 cfg，改 request 级解析」是否真的优于
   任务书字面要求的「补传 cfg」。若判定裁定错误，转新任务而非直接改。
4. **复核 FP-P0-05 的总额论证**：「6000 是净收紧而非放大」这一论证是否成立。
5. **复核 G4 `n/a` 理由**五处是否都站得住。
6. **复核残留是否有漏转**：对照五个任务的实现 diff，看是否有未记录的已知缺口。
