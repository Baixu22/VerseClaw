## Goal（用户可见结果）
Settings 里翻开关后，UI 显示的不是「保存成功」，而是 runtime 真的确认了：
```
saved → pending-restart → restarting → runtime-acknowledged → applied | failed
```
`applied` 只在 child runtime 回报 effective flag 后出现。

## Why this exists
当前 `applied` 的语义是「设置写入成功且 `restart()` 返回」：
- `electron/services/dcs-prod-flags-api.ts:242-271`（restart resolved → `status='applied'`）

这让每一个「已启用」的说法都不可验证 —— 也是 Codex 判定「不能称 liveReady」的直接原因之一。

## Non-goals
- 不改 flag 目录、不新增可写 flag
- 不做 default-on 毕业
- 不做完整遥测管道（→ `FP-P1-06`）

## Acceptance criteria
- [x] 状态机五态全部可达且 UI 可见，含 `failed` 与超时
      — 状态常量 `DCS_FLAG_ACK_STATES`（`shared/dcs/prod-flags-control.ts:19`）；`saved`/`pending-restart` 由 `setDcsProdFlag` 早退路径产出，`restarting`/`runtime-acknowledged`/`applied`/`failed` 由 `collectRuntimeFlagAck` 产出。UI：`statusTone()` 五态配色 + `AckDetail` 组件渲染 trail/hint/child 身份/missing/rejected（`DcsProdFlagsPanel.tsx`）。真跑 trail = `saved→pending-restart→restarting→runtime-acknowledged→applied`
- [x] `applied` 仅在收到完整 ack payload 后置位
      — `collectRuntimeFlagAck` 只在 `isCompleteDcsFlagAck(payload) && generation 匹配 && 无 rejectedFlags` 时 push `applied`；`restart()` 返回后仅到 `restarting`。单测 `dcs-flag-ack.test.ts` 用 `it.each(DCS_FLAG_ACK_REQUIRED_FIELDS)` 逐字段删除验证「七字段缺一不算」（7 个用例）；E2E 断言 `applied` 必带 `runtimeAck`
- [x] 旧世代 child 的 ack 被丢弃（generation 校验）
      — 启动层 `stampGatewayGeneration` 戳 `VERSE_CLAW_GATEWAY_GENERATION`（`process-launcher.ts`），child 读回并回报；host 比对 `expectedGeneration`。不匹配 → `failed` + `ack-stale-generation`（`dcs-flag-ack.test.ts` "discards an old-generation ack"）。E2E 实测 `ackGeneration === gatewayGeneration === "2"`
- [x] ack 超时 → `pending-restart` 或 `failed`，UI 给出可操作提示
      — gateway 仍运行 → `pending-restart` + `ackHint.ackTimeoutRunning`（可重试）；已停止 → `failed` + `ackHint.ackTimeoutStopped`。两条单测分别覆盖。提示为 i18n key，UI 经 `AckDetail` 的 `settings-dcs-flag-ack-hint` 渲染
- [x] `degradedReason` 能透出到 UI 与观测
      — runtime 侧聚合 `config-file-absent` / `partial-flag-reject`；`AckDetail` 在 child 行内输出 `degraded <reason>`；`degradedReason: null` 被显式视为「已回报且无降级」（非缺字段），单测锁定
- [x] `turnEffectProbe` 在 flag off 时报告「未注入」，on 时报告「已注入」
      — off：E2E 实测 `{"wouldChangeTurn":false,"activeSurfaces":[]}`；on：FP-P0-04 setFlag E2E 断言 `wouldChangeTurn === true`；kill 态：`killSwitchEngaged:true` 且 `activeSurfaces:[]`（FP-P0-02 E2E 实测）
- [x] 单测覆盖：正常 ack、超时、旧世代、部分 flag rejected
      — `tests/unit/dcs-flag-ack.test.ts` 18 passed（含七字段逐一、非对象载荷、延迟数轮后应答）；`openclaw_runtime/src/context-engine/runtime-flag-ack.test.ts` 16 passed（child 侧构造、kill 归零、rejected 表达、hash 稳定性/敏感性、kebab↔snake 映射回归）
- [x] Electron E2E：翻开关 → 真 child ack → UI `applied`
      — `tests/e2e/runtime-launch-contract-fp-p0.spec.ts` 第三条用例经 **真控制面** `dcsProdFlags.setFlag` 翻 `working-memory`，实跑得 `status: applied`、`ackChildPid: 36476`（≠ 主进程）、`ackGeneration` 与 host 期望一致、`ackMissingFields` 为空。3 条 E2E 同跑 `3 passed (9.1m)`。**注**：断言落在控制面返回的状态机结果与真 child ack 上，未驱动 Settings 页面 DOM；DOM 层断言见 Residuals → `FP-P1-03`

## E2E 障碍处置（任务书已知障碍）

任务书提示 `VERSE_CLAW_E2E=1` 跳过 gateway auto-start。**已按「自行新增真 gateway E2E profile」路线解决，未转 Residuals**：
E2E 内经 host `gateway.start` / `settings.set gatewayPort` 显式拉起真 gateway child（`ensureGatewayRunning`），
`setFlag` 传 `restartGateway: true` 强制走产品重启路径。G3 证据是真 child ack，非 mock。

## 途中发现并修复的缺陷

1. **命名不一致导致健康 flag 被误判 rejected**：控制面用 kebab 配置路径寻址
   （`runtime.contextBlock.working-memory.enabled`，见 `DCS_WRITABLE_FLAG_SPECS.targetKey`），
   而 Assembler flag 名是 snake（`working_memory`）。首跑 E2E 得
   `status: failed / failureReason: flag-rejected`，而 flag 其实已正确生效。
   已加 `normalizeRequestedFlagId` 显式映射 + 3 条回归单测（含「拒绝时回报 host 原始 id」）。
   —— 只做单测（两侧都用同一常量）永远发现不了，这是 G3 要求真 child 的第二个价值点。
2. `runtime.flags.ack` 未登记 SAFE 方法 → readOnly workspace 下被 workspace 权限层判为
   mutation 并拒绝（`Read-only mode does not allow Gateway mutations`）。已登记。
