## Goal（用户可见结果）
运维按文档写下的任何 `runtime.*` 配置都能真正被接受；不会出现「文档和类型都说支持、写下去 gateway 却起不来」。

## Why this exists
`FP-P0-02` 实做时发现：`runtime.contextEnhancement` 存在于
`openclaw_runtime/src/config/types.openclaw.ts:284`、被 kill 判定读取、
`schema.labels.ts:779` 与 `schema.help.ts:2079` 都有条目，**但 `zod-schema.ts` 的 strict
schema 里没有这个叶子**。后果不是「配置无效」而是**更糟**：写入该键 → 配置校验失败 →
gateway child 以 `code=1` 退出、完全起不来。

该缺陷已在 `FP-P0-02` 单点修复（`zod-schema.ts` 补 `contextEnhancement`），但**同类风险未被守卫**：
其他「类型有 / schema 无」的叶子可能同样存在，且同样只在真启动时暴露。

## Non-goals
- 不重构 config schema 结构
- 不新增配置项
- 不做配置迁移工具

## Context / code anchors
- `openclaw_runtime/src/config/types.openclaw.ts`（TS 类型，人写）
- `openclaw_runtime/src/config/zod-schema.ts`（运行时校验，strict）
- `openclaw_runtime/src/config/schema.labels.ts` / `schema.help.ts`（UI 文案）
- `FP-P0-02` 的修复点：`zod-schema.ts` 的 `contextEnhancement` 叶子

## 实现要点
1. 先普查现存差集：遍历 `RuntimeFeature` 类型的叶子路径 vs zod schema 接受的路径，列出所有
   「类型有 / schema 无」与「schema 有 / 类型无」。**普查结果先入本文档**，再决定逐个修还是分批。
2. 加自动守卫（测试或 `contract:check` 子步骤），差集非空即失败。
3. `schema.labels.ts` / `schema.help.ts` 的键也应在差集检查内（有文案却写不进去，等价于骗运维）。
4. 守卫必须能被反向验证：临时删一个 schema 叶子 → 守卫失败。
