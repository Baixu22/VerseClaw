## Goal（用户可见结果）
一次真实编码 turn 跑完后，能拿出一份账：本轮注入了多少字符、每个来源各多少、
谁被截断/丢弃、总和与 prompt 实际增长一致。

## Why this exists
`FP-P0-05` 建立了 turn 级共享预算并接入 4 类注入源，但它的 G3 只证明了
**契约在真 child 里是活的**（总额 / precedence / 阈值 / 计数器接口存在且一致）。
真跑输出的 counters 全为 0：

```
[fp-p0-05-budget] {"totalChars":6000,"precedence":[...],"dropAlertRatio":0.1,
  "counters":{"turns":0,"killedTurns":0,"appliedChars":0,"requestedChars":0,
              "droppedChars":0,"truncatedChars":0,"dropAlerts":0}}
```

原因是那条 E2E 没有 provider、没跑 agent turn。所以
**「一次真实 turn 内多源 charge 后账目求和核对」目前只有单测证据**。
`FP-P0-05` 主动把这一项转为残留而没有用单测绿冒充（DoD 禁止的假 done 模式第 5 条）。

## Non-goals
- 不改预算算法与 precedence（那是 `FP-P0-05` 的裁定，除非发现实测矛盾）
- 不做阈值调参（→ `FP-P2-04`）

## 实现要点
1. 复用 W5 的 `startQaMockOpenAiServer` + `mock-openai` provider 跑真 agent turn。
2. 开启多个注入源（working-memory + tool-registry + 至少一个 orchestrator 源），
   让同一 turn 内确实有 ≥2 个来源 charge。
3. 断言 `counters.turns >= 1` 且 `appliedChars > 0`。
4. **求和核对**：`appliedChars + droppedChars + truncatedChars === requestedChars`。
5. 再核对 `appliedChars` 与该 turn prompt 实际增长量一致（这是账目诚实性的关键，
   也是唯一能发现「charge 了却注入了别的文本」这类 bug 的断言）。
6. 造一次超预算场景（塞大内容），断言 `degradationOrder` 与 precedence 一致、
   且被裁的是后序来源。

## Acceptance criteria
- [x] 真实 turn 后 `counters.turns >= 1`、`appliedChars > 0`
      → `[fp-p1-04-budget] {"turns":1,...,"appliedChars":6000}`（真 agent turn，非单测）
- [x] 求和核对成立（applied + dropped + truncated == requested）
      → `6000 + 0 + 2000 = 8000`；聚合计数器与 `lastTurn` **两个层级各断言一次**
- [ ] `appliedChars` 与 prompt 实际增长一致（不只是内部自洽）
      → **部分**：`chargeAppendedSegment` 把 charge 后文本写回 prompt（代码级保证 ledger 与 prompt 不会分歧），
        但未做独立的 prompt 长度测量比对 → 残留 **FP-P2-06**
- [ ] 同一 turn 内 ≥2 个来源出现在 `byChannel`
      → **未达成，且查出更严重的真缺陷**：穷举 charge 点后确认全仓只有 3 处
        （`attempt.ts:3273` cvk_addition、`context-orchestrator.ts:316` memory_pilot、`:360` vtoken）。
        声明的 7 项 precedence 中 **`knowledge` / `working_memory` / `tool_registry` 三项没有任何 charge 点**，
        即 **DCS 三块的注入不受该共享预算约束、也不被记账** —— 不是「本轮没开」，是「开了也不会出现」。
        （初判「三块被合成 cvk_addition」经复核为错：`cvk_addition` 是 CVK 自身文本，见 `cvk/engine.ts:119-190`。）
        → 转 **FP-P2-06**
- [ ] 超预算场景下降级顺序与 `TURN_INJECTION_PRECEDENCE` 一致
      → **部分**：通用校验已写入 E2E（被裁通道位次不得早于任何完整保留通道），
        但本轮仅单通道 truncate，不构成对排序的有力验证 → 残留 **FP-P2-06**
- [x] kill 态真 turn 账目归零（与 `FP-P0-02` 一致）
      → `killedTurns` 计数器在案 + FP-P0-02 真 child kill 证据；本轮 `killed:false` 为非 kill 场景

## Decision

1. **不新建 E2E，复用 `coding-loop-fp-p1-04.spec.ts`**。它已是真 Electron + 真 child + 真 agent turn，
   另起一条会重复 25 分钟量级的启动成本且证据同源。任务书建议的 W5 mock provider 路线等价。
2. **新增「最近一轮」逐通道明细面**。聚合计数器答不了「哪些来源 charge 了 / 降级是否符合 precedence」，
   故在 observability 保留 `lastTurnInjection` 并由 ack 暴露为 `injectionBudget.lastTurn`。
   只增读侧证据，不改预算算法与 precedence（Non-goals）。
3. **AC4 不靠打开排除组件凑数**。为让 `byChannel` 出现第二个来源，唯一手段是启用 VToken 或 RM 注入 ——
   两者都是 Hard locks 排除项。宁可让该条 AC 标未达成，也不为过测放宽标准。
   替代断言（每个 charge 过的通道必须在声明 precedence 表内）能抓通道漂移，是真守卫而非占位。
4. **本任务不标 done，并后置为 `deferred`**。AC4 未达成、AC3/AC5 仅部分，按 DoD「五门禁缺一不许标 done，
   不接受 done-with-residuals」。剩余实现与验收已完整转交 `FP-P2-06`，本任务不再占用 P1 active；
   已完成部分（真 turn 非零账目 + 求和核对 + `lastTurn` 逐通道证据面）作为阶段性成果保留。
5. **补三个缺失 charge 点不在本任务做**。那是改预算接入面（FP-P0-05 裁定域），
   且会改变真实注入行为（可能截断此前不受限的 DCS 内容），风险不属「核对账目」的范围。
