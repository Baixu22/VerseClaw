## Goal（用户可见结果）
新用户走完 Setup 后，**必然**已经有一个被验证过的 Provider 与可用 Model；不存在「跳过即完成、进主界面才发现没法用」的路径。

## Why this exists
现在 Setup 只有 Welcome → Runtime → Installing → Complete（`src/pages/Setup/index.tsx:38-43`），ProviderContent 已删除，Skip 可直接完成。首产品的第一句承诺是「安装 → 第一次成功编码任务」，而当前安装完成后离可用还差整个 Provider 配置。

## Non-goals
- 不做 Provider 管理全功能页（Settings 已有）
- 不内置任何厂商密钥
- 不做模型推荐/比价

- [x] 校验失败给出可操作文案（改什么、去哪改），不是原始错误串 → 每类失败有 title+action 双句文案（改哪里、去哪拿 key）；原始错误串仅作为小字附注保留

- [x] 凭据只走安全存储；任何日志/截图/support bundle 中不含 key → key 仅经 `createAccount(account, apiKey)` 走既有安全存储路径；持久化的 `setupProviderVerification` 与 `metadata.validation` 为脱敏结构；E2E 断言序列化结果不含 key

## Decision（实现裁定）

1. **E2E 端点策略**：不 mock 校验请求（硬锁）。E2E 起真实本地 HTTP 服务器实现
   OpenAI 兼容 /models 面；electron main 的 provider-validation 对其发真实网络请求。
   401 由真服务器返回、网络不可达用真关闭端口 —— 即 FP-P1-07 任务书 A 路线的同款模式。
2. **「模型最小可用性验证」定义**：选中模型必须出现在该账号实时拉取的 /models 列表中
   （记录 checkedAt）。未做 1-token 真实补全探测：后端无该 action，新增会扩大改动面，
   且列表存在性已强于现状（现状为零验证）。残留见 Residuals。
3. **验证状态持久化**：新增 AppSettings/SettingsSnapshot 键 `setupProviderVerification`
   与 ProviderAccount `metadata.validation`（三处类型副本同步），均为脱敏结构，
   直接服务 FP-P1-06 support bundle 的「Provider 类型与验证状态要有、key 不能有」。
4. **Skip 保留**：首启硬阻断会把无网/内网用户挡死在向导里；改为「跳过=显式受限模式 +
   首次发消息拦截」，与 AC 的条件式表述一致。
