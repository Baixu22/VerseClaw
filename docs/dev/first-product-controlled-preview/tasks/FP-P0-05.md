## Goal（用户可见结果）
多路注入（DCS / VToken / Runtime Memory / CVK）共用一份可观测预算，超限时按明确优先级降级，并在观测里显示是谁被裁、裁了多少。

## Why this exists
现状是各自为政：`Assembler` 内有 `createInjectionBudget`（`assembler.ts:150`）覆盖 DCS transformContext，但 VToken / RM / CVK 不在同一账上；CVK 与 Assembler 存在双投影，precedence 未统一。首发承诺「token/latency 最小观测」，账目不统一就无法解释「为什么这轮 context 变短了」。

## Non-goals
- 不做 C6 自动 context ladder
- 不新增注入源
- 不改单一注入源的内部算法

### 1. precedence（固定顺序，非按 request 动态）

```
knowledge > working_memory > tool_registry > cvk_addition > vtoken > memory_pilot > other
```

**判据：按「丢掉它是否会让这一轮变错」排序，而不是按注入源的归属系统排序。**

- `knowledge`（compass / role-memory）承载目标与角色约束 —— 丢掉会让 agent 做错事。
- `working_memory` 承载「刚做过什么」 —— 丢掉会重复劳动（实测最贵的失败模式）。
- `tool_registry` 是**可恢复**的：模型看不到工具摘要仍能调用工具，只是少一层提示。
- `cvk_addition` / `vtoken` / `memory_pilot` 是**增益**：有价值，但缺了这一轮依然正确。

否决「按 request 类型动态」的理由：动态顺序让降级不可复现，运维无法回答
「为什么这轮 context 变短了」—— 而这正是本任务要交付的可解释性。任务书候选顺序
`DCS > CVK > VToken > RM` 与本裁定在跨系统层面一致（DCS 三通道在前，CVK 次之，
VToken、RM 最后），本裁定只是把 DCS 内部三通道按重要性再拆开。

### 2. 预算口径：**字符**，单一扁平池，不分层

- **字符而非 token**：现有全部注入点已按字符计量
  （`applyInjectionBudget`、`recordCvkSystemPromptAddition`、orchestrator lineage 的 `chars`）。
  字符精确、与 provider 无关；token 需要按 provider 装 tokenizer，会导致
  「记账口径」与「执行口径」互相不一致，且无法诚实求和。
  VToken 内部仍保留自己的 `budgetTokens` 做打包 —— 那是「怎么压缩」，与
  「这一轮允许 prompt 长多少」是两件事。
- **扁平而非分层**：分层会出现「空闲通道占着配额不用、繁忙通道却在截断」的浪费。
  precedence 已经防止重要通道被饿死，不需要再用配额保护。
- **总额 `TURN_INJECTION_CHAR_BUDGET = 6000`**：原 `KNOWLEDGE_INJECTION_CHAR_BUDGET`
  为 2000，且只覆盖 DCS 三通道；现在同一个池要装 6 个来源。6000 = 2000（DCS 原额，不缩水）
  + 约 4000 给 CVK/VToken/RM 三个此前完全不受约束的来源。**这不是「放大总预算消除降级」**
  （Hard lock）：此前这三个来源是 **0 约束**，把它们纳入一个有限池是净收紧；
  DCS 三通道的可用额度与改动前完全一致。

### 3. degraded 语义（三态在观测中可区分）

| 语义 | 判定 | 含义 |
|---|---|---|
| `skip` | `charsRequested === 0` | 该源没跑（flag off / kill / 无内容）。**不是降级** |
| `truncate` | `0 < charsApplied < charsRequested` | charge 了，装不下，注入了前缀 |
| `drop` | `charsApplied === 0 && charsRequested > 0` | charge 了，一个字都没注入 |
| `applied` | `charsApplied === charsRequested` | 完整注入 |

三态各自带 `channel` 来源标签，并按 charge 顺序记入 `degradationOrder`，
所以「谁被裁、裁了多少、按什么顺序裁」都可复现。
关键区分：`skip` 与 `drop` 绝不混淆 —— 前者是「本来就没有」，后者是「有但被预算挤掉」，
混为一谈会让运维误判预算是否吃紧。

### 4. 运营阈值：drop 比例 > **10%** 告警

`TURN_INJECTION_DROP_ALERT_RATIO = 0.1`，分子为
`droppedChars + truncatedChars`（丢失的字符总量），分母为该 turn 总预算。
超过即置 `alert: true` 并累加 `dcs.turnInjection.dropAlerts`。

10% 是 controlled preview 的**起始线**，不是经验值：低于此认为是正常的预算竞争，
高于此说明这一轮已经在丢可观测量级的上下文。**必须用真实 canary 数据复核并调整
（→ Residuals `FP-P2-04`），且调整方向不得是「放大总预算让告警消失」。**

## Acceptance criteria
- [x] 一次 turn 内所有注入源共享同一预算实例，账目可求和核对
      — `beginTurnInjectionBudget({turnId})` 按 turnId 返回**同一实例**（`turn-injection-budget.test.ts` "all sources in one turn share a single budget instance" 断言第二次取到 `toBe` 同一对象且能看到第一次的花费）。turnId 由 `attempt.ts` 按 `sessionKey::runId` 生成，orchestrator（VToken/RM）、Assembler（DCS 三通道）、CVK addition 全部传同一个。求和核对：`charsApplied + charsDropped + charsTruncated === charsRequested` 被单测断言
- [x] precedence 明文化并被测试固定
      — `TURN_INJECTION_PRECEDENCE` 常量 + `## Decision` 第 1 条书面理由；单测断言相邻两两严格递增且无重复；真 child ack 回报该顺序（E2E 实测 `["knowledge","working_memory","tool_registry","cvk_addition","vtoken","memory_pilot","other"]`）
- [x] 超限时降级顺序确定、可复现
      — `turn-injection-budget.test.ts` "degrades later-precedence sources first and the order is reproducible"：同一输入跑两次，`degradationOrder` 深度相等；且断言前两个通道完整注入、`tool_registry` truncate、`vtoken` drop
- [x] `drop / truncate / skip` 在观测中可区分，带来源标签
      — 每个 entry 带 `channel` + `disposition`；`byChannel` 按来源聚合；`summarizeTurnInjection` 分别产出 `charsDropped` / `charsTruncated`。单测 "distinguishes drop / truncate / skip in observation" 与 "treats an empty/absent injection as skip, not as a drop" 分别锁定四态与 skip≠drop
- [x] kill 生效时预算账目显示归零（与 `FP-P0-02` 一致）
      — `killed: true` 建零额账本，所有 charge 记 `skip`/0。单测断言 `total=0, charsApplied=0, charsRequested=0, charsDropped=0, dropRatio=0, alert=false`；`assembler.kill-switch.test.ts` 亦断言 kill 时无注入。真 child：FP-P0-02 E2E `killSwitchEngaged:true` + `activeSurfaces:[]`
- [x] 运营阈值写入文档且可配置
      — 阈值 `TURN_INJECTION_DROP_ALERT_RATIO = 0.1` 与理由写入 `## Decision` 第 4 条；`beginTurnInjectionBudget` 接受 `total` 覆盖。**诚实说明**：阈值本身目前是导出常量（改需改码），未做 openclaw config 化 —— 见 Residuals `FP-P2-04`
- [x] 指标口径**唯一**：修掉 C1 `decision.json` 5.125x 与 report 4.5x 的口径分歧，或明确两者定义差异
      — 裁定为**同公式、异语料**（均为 `mean(off)/mean(on)` 比值之比）。已实算复核：`coding-c1` 4 条手写 fixture → mean off 4.5 / on 1.0 → 4.5x；`dcs-canary/c1` 32 条合成语料 → 5.125x。两处 artifact **各自**加 `reductionDefinition`（公式/语料/fixture 数/live 标记/互相指向），并写 `artifacts/first-product-preview/FP-P0-05/reduction-factor-reconciliation.md` 说明为何不应相等。**未删任何数字、未改任何门禁结论**（两者仍 `meetsGate:false` / `keep-off`）。语料统一属方法学变更 → Residuals `FP-P4-05`

### G3 证据的诚实边界

E2E 证明的是：**共享预算契约（总额 / precedence / 阈值 / 计数器接口）在真 child 里是活的**
—— child 自报的 precedence 与代码常量一致，7 个计数器都存在且可求和。

**未证明的是计数器在真实 agent turn 下的非零行为**：上面 `counters` 全为 0，
因为这条 E2E 没有跑 agent turn（无 provider）。因此
「一次真实 turn 内多源 charge 后账目求和核对」目前只有单测证据。
这一项**不算已验证**，转 Residuals `FP-P1-11`，将在 FP-P1-04（编码任务闭环，有真 provider）
的链路里取真实非零账目。不用「单测绿」冒充这一项。
