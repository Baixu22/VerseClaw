Task Forest 是研发追踪 skill。产品运行不读取该 skill、任务森林目录、TF 编号或开发会话历史。本方案以应用既有 Task Ledger 为产品任务 owner；VG 作为候选、工作树与验证证据的适配器，运行状态仍由既有 TaskFlow / execution owner 维护。

**问题包含六个相互关联的方面。** 对话摘要会丢失验收条件；任务、会话和单次 run 的身份混用；事件追加缺少跨进程事务；租约到期无法证明旧进程停止；恢复只留下文本而缺少产物与在途操作；执行成功与业务验收成功缺少可靠的关联。只给任务加一个 owner 字段无法解决后面几项。

**研究结论落实为以下代码约束。** 原始检索使用 versesearch 的 Exa Search 路线，来源索引为同目录 `sources.json`。

| 来源 | 抽取的机制 | 本项目采用方式 |
|---|---|---|
| Temporal Workflow ID / Run ID、执行历史 | 稳定业务身份与多次运行分离，失败后重建状态 | taskNodeId 恒定；attempt、run、session generation 独立记录；压缩摘要不是目标来源 |
| Kubernetes Controller / resourceVersion | 目标状态与实际状态分离；版本冲突显式拒绝 | 目标契约 revision 与执行 epoch 分离；所有修改有预期版本；恢复根据 owner 事实核对 |
| Camunda user task lifecycle | 候选人、领取、归属与执行状态分离 | owner 长期保留；暂停不等于退回队列；交接是受控状态转换 |
| AWS 幂等 API、outbox、重试设计 | 请求身份识别重试；超时可能已有副作用 | 同 key 同参数返回已有结果；异参拒绝；未知操作保留并阻止盲重试 |
| Kanban Guide | 显式开始/完成规则、WIP 限制、按容量拉取 | 可领取性由状态、依赖、资格、资源容量共同决定；聚合目标不当作实现叶子派发 |
| HSE 交接设计 | 固定关键信息、书面记录、接手方复核 | 结构化检查点包含目标、产物、下一步与未知事项；接手时验证版本和候选 |
| Kleppmann fencing 分析 | 租约到期后仍可能有旧客户端写入 | 单调 epoch 与目标端校验；在途操作未排空时禁止转移 writer |

**身份与任务识别采用分层规则。** 显式 taskNodeId 是最强关联；外部工单等稳定 business key 可解析到已有任务；相同意图的幂等请求返回同一对象。相同标题、相似描述、相同路径只能作为重复候选，不能自动合并任务。精确规范化契约指纹可识别同一项目内尚未结束的重复提案；明确的新发生实例保留独立 occurrence key。工作树路径不进入任务排他键。

讨论模式不创建任务。明确进入执行时保存目标契约，并建立持久 session binding；后续继续、状态询问和上下文压缩沿用该绑定。修改目标使用带 expectedRevision 的显式修订，不从最近一条消息覆盖原始目标。契约包含 objective、expected outcomes、constraints、acceptance criteria、依赖、目标范围与来源。原始目标与每次修订保留历史。

**所有权沿用 Task Ledger，持久层使用本机 SQLite。** 产品任务事件、目标契约、领取、检查点和操作回执放在同一 owner 的事务边界中。旧 JSONL 经显式、可重试的导入接续，保留源文件与原 ID；读取遇到损坏、权限或数据库错误时不得返回一份空任务图。开发 Task Forest 的 JSON 不参与迁移。

Git 工作树按规范化的 git-common-dir 定位同一仓库任务域；普通目录按规范化根路径定位；缺路径保持不可用。应用 workspace 是执行/权限上下文，仓库任务域是共享任务命名空间，二者保留关联。独立 clone 或远程机器需要单一协调服务端才能共享领取资格；首版保持本机文件系统事务边界，禁止用数据库文件同步模拟分布式互斥。

**领取采用一个短事务。** 事务核验任务类型、依赖、契约版本、owner、暂停/取消状态和请求幂等键，随后写入 claim 与历史。claim 携带 sessionKey、generation、worktree、epoch、attempt。epoch 永不因释放而归零。创建工作树、调用模型或派发实现 worker 位于成功领取之后。

| 操作 | 条件 | 结果 |
|---|---|---|
| claim | 任务可执行、依赖已完成、未被有效归属占用 | 唯一 owner 和新 epoch |
| renew / checkpoint | 当前 session/generation/epoch 与契约版本一致 | 续期或持久化进度；不改变目标 |
| pause | 当前 owner，无未决工具操作 | 保留归属与检查点 |
| handoff / recover | 旧执行已排空或已由资源 owner 证明隔离 | 提升 epoch、新 owner 接续；旧凭证被拒绝 |
| submit | 当前 owner、候选绑定、验收输入完整 | 进入 review；保留实现资格直到接受或修复 |
| accept | 验证器核对契约、候选、真实检查与产物 | Task Ledger 记录完成并释放执行资格 |
| cancel / release | 保存待恢复产物，处理在途操作 | 记录原因与产物归宿，不删除工作树 |

租约过期进入 recovery_required，不自动把任务交给新会话。在途工具调用持久登记；进程崩溃留下 unknown，不当作没有执行。目标端检查与副作用之间的竞态通过操作占用和交接排空约束处理。普通终端或未接入协议的外部客户端不能获得相同的强制保证，产品必须显示实际覆盖级别。

**目标恢复在模型调用边界完成。** 从持久 task binding 读取当前契约、最近有效检查点和阻塞项，构造有长度上限的任务上下文。该上下文每次启动/恢复执行时重新装配，不依赖压缩后的 transcript。契约核心超预算时拒绝执行并报告具体字段；可选历史与证据正文改为引用。goal digest、revision 与注入回执可查，缓存按 revision/epoch 失效。

**任务系统与现有项目的接线如下。** Main 的 Task Ledger API 负责身份解析、目标修订与领取；chat send 在发往 Gateway 前核对执行资格和恢复目标；runtime 工具包装在实际调用前登记操作并在返回后记录结果；派发、fork 和 handoff 读取同一资格；Task Ledger 页面展示任务目标、归属、工作树、恢复状态和验收状态。Renderer 只经 hostApi 访问。VG 接收任务/候选关联，不另建任务完成 owner。

**验收由要求到证据逐项闭合。** 每个 acceptance criterion 有稳定 ID 和验证种类；执行器运行完成、模型文本、exit 0 均不能单独关闭任务。文件检查应实际读取字节并记录哈希；命令检查绑定 argv、cwd、候选与退出码；独立评审由现有 verifier/effect owner 的回执引用进入完成规则。未知或缺失验证保持 review。任务图更新与外部证据写入之间使用操作 ID、待处理记录和恢复核对，禁止伪装成跨存储原子事务。

**降级保持目标可读、执行资格保守。** 数据库不可用时允许显示已明确标注陈旧的只读缓存，拒绝领取/交接/完成；模型不可用时保留任务与下一步；VG 不可用时保留开发产物，阻止要求 VG 验证的完成；上下文预算不足时保留关键目标并停止写入；证据服务不可用时停在 review；时钟回退、休眠和宿主 generation 变化均触发重新准入。所有恢复步骤由脚本或 agent 执行。

**性能开销需要可复算的边界。** 任务身份和当前状态使用索引点查；每个工具动作不重放整份事件日志；事件/检查点有体积上限和分页；心跳只更新租约，不重写目标或完整快照；不为每个任务增建轮询器。验收测量 1k/10k 任务下的识别、领取、续租、上下文读取 p50/p95、数据库增长、上下文字符预算、缓存命中及同机 16 进程争抢。先记录环境基线，再设定实测预算，禁止将无法启动的测试记成通过。
