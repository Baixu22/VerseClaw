# P3 issue 153

`harness/specs/rules/dcs-stage5-sekb-closure-boundary.md` was the only
checked-in spec that could not pass the repository's own `harness validate`. It
declared `type: ai-coding-rule` yet also carried a task-style
`scenario: gateway-backend-communication` key. `cli.mjs` classified specs by
that key (`isGatewayBackendCommunicationTask`), so the rule spec was routed into
`validateGatewayTaskSpec` and failed on every task-only field:

```
- harness\specs\rules\dcs-stage5-sekb-closure-boundary.md: missing required field "taskType"
- harness\specs\rules\dcs-stage5-sekb-closure-boundary.md: gateway backend communication tasks must set taskType: runtime-bridge
- harness\specs\rules\dcs-stage5-sekb-closure-boundary.md: requiredProfiles must include "fast"
- harness\specs\rules\dcs-stage5-sekb-closure-boundary.md: touchedAreas must declare affected paths
- harness\specs\rules\dcs-stage5-sekb-closure-boundary.md: acceptance must declare completion criteria
- harness\specs\rules\dcs-stage5-sekb-closure-boundary.md: docs.required must be explicitly true or false
```

The issue listed two fix directions: pad the rule spec with task-only fields, or
move it out of `rules/` and unwind the task specs that reference it. Both treat
the symptom. The defect is the classifier: `scenario:`/`scenarios:` is
scenario-applicability metadata that rule, guide and layer specs legitimately
carry, and it is not a task declaration. Task identity comes from the spec
location.

## Changes

- `harness/src/specs.mjs` adds `isTaskSpec`, which returns true only for specs
  under `harness/specs/tasks/` (pathless unit fixtures keep the legacy
  behaviour unless they declare a non-task `type`).
  `isGatewayBackendCommunicationTask` and `isPluginLifecycleTask` now return
  false for non-task specs.
- `harness/specs/rules/dcs-stage5-sekb-closure-boundary.md` drops the vestigial
  `scenario:` key; `appliesTo` already routes it into the scenario.
- `tests/unit/harness-specs.test.ts` pins the classifier with three regression
  tests: rule specs are not tasks, a rule spec with a scenario key is not a
  scenario-bound task, and a real task spec with a scenario key still is.
