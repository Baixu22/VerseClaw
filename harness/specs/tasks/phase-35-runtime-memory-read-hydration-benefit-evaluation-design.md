# Phase 35 Runtime Memory Read Hydration Benefit Evaluation Design

Phase 35 designs and implements an independent mock quantitative benefit evaluation for Runtime Memory read hydration. It builds on the Phase 34 limited production opt-in evidence and answers the question: does the existing guarded consumer show a real benefit signal over baseline and naive memory arms, without any production cutover, default TaskLoop connection, user Runtime Memory DB read, prompt/context/model-message injection, or runtime/durable fact authority?

This phase is evaluation only. It does not default-enable read hydration, does not connect the default TaskLoop path, does not read user Runtime Memory DBs, does not add Gateway/IPC/renderer/host-api/api-client/shared contract surfaces, does not change provider/tool ordering, and does not let evaluation results become runtime authority or durable fact authority.

## Hard Boundaries

- No default runtime switch. No default TaskLoop read hydration. No default shadow helper call.
- No Gateway route, Electron IPC route, renderer page/component/UI, host-api/api-client/shared contract, or direct Gateway HTTP/WebSocket renderer call.
- No hydration facts or evaluation results in prompt assembly, context provider output, model messages, Gateway/provider transport payloads, runtime decisions, next actions, checkpoints, transcripts, lifecycle events, traces, durable memory writes, provider ordering, or tool selection.
- No real LLM/provider/model endpoint calls. Scoring is deterministic.
- No reading or writing user Runtime Memory databases. Only controlled sanitized temporary fixture DBs under `os.tmpdir()` are permitted, and only through the existing explicit diagnostics path.
- No bypassing sanitizer boundaries, no raw SQLite rows, no `record_json`, no raw chat/transcript/jsonl/trace/prompt/payload/tool args/tool output/env/secret/traceparent/tracestate/baggage, no authority markers.
- The consumer remains a pure function. The evaluation must not open, read, create, migrate, or write production SQLite databases, and must not call TaskLoop, provider, Gateway, IPC, host-api, api-client, or any service/listener/daemon/server.

## Dataset Requirements

The Phase 35 corpus is generated by `tests/fixtures/runtime-memory-benefit-eval/generate.mjs` and committed as JSON fixtures under `tests/fixtures/runtime-memory-benefit-eval/`.

- 500-2000 mock memory facts.
- At least 8 scenario categories:
  1. `repo_conventions` — package manager, test command, formatter, file boundary.
  2. `user_preferences` — reply language, style, forbidden action.
  3. `project_architecture` — renderer/main boundary, host-api, Gateway, runtime helper.
  4. `task_history` — previous failed approach, validated file, tests already run.
  5. `negative_memory` — expired, invalidated, future-valid facts.
  6. `conflict_memory` — same taskId/subject/predicate candidates with exactly one correct winner.
  7. `hazard_memory` — prompt-injection sentinel, raw-leak sentinel, secret-like text, tool args.
  8. `distractor_memory` — taskId/subject/predicate mismatch but semantically nearby.
- At least 100 queries, each with `queryId`, `taskId`, `subject`, `predicate`, `referenceTime`, `tokenBudget`, `limit`, `expectedFactIds`, `mustRejectFactIds`, `scenarioId`.
- Three evaluation arms in `scenarios.json`:
  - `baseline` — no memory.
  - `naiveMemory` — direct same-key match, sorted by confidence, sliced to `limit`. Negative control.
  - `guardedMemory` — `consumeRuntimeMemoryHydrationFacts` result. Positive control.
- Each fact carries at least: `factId`, `taskId`, `subject`, `predicate`, `objectSummary`, `recordKind` (`"fact" | "candidate"`), `verificationStatus`, `valid_at`, `invalid_at` / `expired_at` optional, `reference_time`, `confidence`, `sourceEpisodeRefs`, `evidenceRefs`, `labels`.

## Metrics And Thresholds

The focused unit test computes a deterministic evaluator over the corpus and asserts:

| Metric | Threshold |
|---|---|
| `guardedRecallAtK` | >= 0.95 |
| `guardedPrecision` | >= 0.98 |
| `staleInvalidSuppressionRate` | = 1 |
| `candidateRejectedSuppressionRate` | = 1 |
| `conflictSuppressionRate` | = 1 |
| `taskSubjectPredicateIsolationRate` | = 1 |
| `rawLeakRate` | = 0 |
| `promptInjectionReturnRate` | = 0 |
| `wrongConflictWinnerRate` | <= 0.02 |
| `emptyNoOpSafetyRate` | = 1 |
| `guardedVsBaselineLiftMemoryDependent` | >= 0.15 on memory-dependent scenarios |
| guarded memory success rate on memory-irrelevant scenarios | must not drop below baseline |
| `guardedVsNaiveHazardReduction` | > 0.9 |
| pure consumer latency p95 | < 50 ms |
| temp SQLite hydration + consumer latency p95 | < 500 ms |

## Deterministic Scoring Rules

The evaluator does not call real models. Scoring is deterministic:

- If `scenario.requiredFactIds` are all in accepted facts, memory-assisted success +1.
- If accepted facts include `mustRejectFactIds` or hazard labels, violation +1.
- If baseline lacks required facts, baseline fails.
- `naiveMemory` may retrieve required facts but also retrieves hazard/stale/conflict, so it is counted as risk or failure.
- `guardedMemory` should succeed with no hazard.

## Validation

Phase 35 must run all `requiredTests`. The deep-validation handoff records the dataset structure, metric definitions, observed metric table, three-arm comparison, hazard suppression, token/latency distribution, conclusion on whether a real benefit signal exists, and the Phase 36 hard gates required before any broader agent/LLM scenario.

## Phase 36 Hard Gates

Phase 36 may start only with a fresh task spec and all of these preconditions:

- Keep read hydration default-off and require explicit operator opt-in.
- Keep any limited production opt-in diagnostics-only and shadow-only; no runtime cutover.
- Define operator owner, approval refs, participant/corpus scope, expiry, renewal, and kill-switch operation for any broader corpus.
- Do not read user Runtime Memory DBs until a fresh spec explicitly accepts that scope with privacy/security review and controlled substitute tests.
- Keep diagnostics out of prompt assembly, context provider output, model messages, checkpoints, transcripts, lifecycle events, traces, provider/tool inputs, and durable memory writes.
- Preserve guard gates for record kind, verification status, temporal validity, task/subject/predicate match, prompt-injection sentinel, raw-leak sentinel, conflicts, token budget, and result limit.
- Preserve TaskLoop decision delta count 0, tool/provider ordering delta count 0, prompt/context/model-message/checkpoint/transcript/lifecycle/trace injection count 0, raw leak rate 0, prompt injection return rate 0, durable memory write count 0, and threshold violations 0.
- Do not add Gateway routes, Electron IPC routes, renderer UI, host-api/api-client/shared contracts, provider ordering changes, or default runtime feature switches unless a future spec explicitly accepts that surface and runs its required validation.
- Any transition from mock benefit evaluation to real agent/LLM scenarios requires a fresh spec that adds privacy review, security review, evaluation review, rollback review, and operator gate review on top of the Phase 35 evidence.
