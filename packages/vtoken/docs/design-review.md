# Verse Token v0.3.1 设计审查报告

> 第五轮对抗性审查（落地前审查）。分三档：
> **A 类** = 规格自相矛盾，不修无法实现；**B 类** = 欠定义，落地必须裁决；**C 类** = 战略风险，不改架构但必须警惕。
> 每项标注规格出处，并给出本次落地采用的裁决（与 `DECISIONS.md` 对应）。

---

## A 类：规格自相矛盾（必须修）

### D1. 旗舰示例违反自身的 ID 唯一性规则
- **出处**：§3.2 示例中 `DESC auth.overview` 出现两次，且与 `DEF auth.overview` 共享 ID；而 §8.1 要求"节点 ID 在文件内唯一"，§12 验收要求重复 ID 报错。规格书自己的示例文件无法通过自己的编译器。
- **裁决**：区分**定义类型**（DEF / RULE / VAR / OPEN）与**注解类型**（DESC / EX / META / SRC）。
  - 首个携带某 ID 的行创建节点，该行类型为节点主类型；
  - 后续同 ID 行仅当类型为注解类型时合法，追加为节点的一个 facet（part）；
  - 同 ID 再次出现定义类型 → `duplicate_id` 错误（保留 §12 验收语义）。
  - TIR 输出相应调整为"每行一个语义原子"（一个节点可产出多行，每行带 `[#id:TYPE]` 前缀），比"每行一个节点"更忠实于 §10.2 的"一行一语义原子"原则。
  - 副作用：注解行先于定义行出现时，节点主类型为注解类型，之后的 DEF 会报 duplicate_id——即定义行必须先行。已文档化。

### D2. `created_at` 时间戳破坏 compile 幂等性
- **出处**：§4.1 `VTNode.created_at: int`（Unix ms）；§8.1 要求"相同 .vt 内容 → 相同 .vtg 输出（SHA-256 相同）"。把墙钟时间写进 .vtg 必然破坏该保证。`source_file` 若存绝对路径同理（同内容不同路径 → 不同哈希）。
- **裁决**：doc 模式 .vtg **不含任何时间戳与文件路径**；`created_at` 仅对 mem 节点有意义；`source_file` 在加载 .vtg 时由 loader 注入内存对象，不落盘。行号可以落盘（由内容决定，不破坏幂等）。

### D3. 持久化保证自相矛盾（fsync 语义）
- **出处**：§5.2 说"函数返回后 WAL 已持久化（进程崩溃不丢数据）"；§5.4 说"最坏情况丢失最后一次 fsync 之后的写入（窗口 < 1ms）"。二者互斥：前者要求逐写 fsync，后者描述的是组提交。§5.2 的延迟表"< 5ms（WAL fsync 情况）"也暗示 fsync 不是每次都发生。
- **裁决**：`durability` 参数化：
  - `"fsync"`（默认）：每次 write 后 `os.fsync`，兑现 §5.2 的强保证，延迟以实测为准；
  - `"flush"`：只 flush 到 OS 缓冲，对应 §5.4 的弱保证（掉电/内核崩溃有窗口，进程崩溃不丢）。
  - 文档明确写出两档各自的真实保证，不再含糊。

### D4. 崩溃恢复校验不变式错误
- **出处**：§5.4 Step 3 "内存图节点数 ≥ 快照节点数（只增不减）"。WAL 含 `delete` op（§5.3），checkpoint 之后重放 delete 会使节点数**小于**快照数，该不变式为假。
- **裁决**：删除该不变式。恢复正确性来自：按序重放 + 重放操作幂等（write 重放 = 覆盖写，delete 重放 = 无害 no-op）+ 序号单调恢复。恢复后输出 recovery 摘要（快照节点数 / 重放 op 数 / 是否跳过残缺尾行）供上层校验。

### D5. WAL 有 `delete` op，但 API 面没有删除入口
- **出处**：§5.3 WAL 示例含 `{"op":"delete",...}`；§5.2 只定义了 `vt.write()`。删除记录没有产生者。
- **裁决**：补 `vt.delete(node_id) -> bool`（mem 专用）。删除节点时双向清理邻接边；被引用方悬空按 D12 规则处理。doc 模式的删除 = 编辑 .vt 后重新 compile，不提供运行时删除。

### D6. `%mode mem` 的 .vt 语法是"死分支"
- **出处**：§3.3 定义了 mem 模式的 .vt 文件语法，但 §5.1 明确 mem 写入路径是 `vt.write() → 内存图 + WAL`，从不产生也从不消费 .vt 文件。§2.1 说 mem 的 `.vt` 是"编译源"，§10.3 又禁止对 mem 调用 compile——这段语法在架构里没有生产者也没有消费者。
- **裁决**：定位为**导入/导出格式**（不在热路径上）：
  - parser 支持解析（P1.1 本来就要求）；
  - `MemStore.import_vt()` 把 mem .vt 文件按行经 `write()` 灌入（用于迁移/引导）；
  - `MemStore.export_vt()` 把当前会话渲染回 mem .vt 文本（用于人类查看/归档）。
  - `vt compile` 遇到 `%mode mem` 文件报 `mem_not_compilable` 错误（呼应 §10.3 的禁止项）。

### D7. `os.rename` 在 Windows 上不是原子替换
- **出处**：§5.1、§8.1 多处写 `os.rename(.vtg.new → .vtg)`。Windows 上目标存在时 `os.rename` 抛 `FileExistsError`，第二次 compile 即失败。本项目开发机就是 win32，这不是理论问题。
- **裁决**：全部使用 `os.replace`（POSIX 与 Windows 均为原子替换）。写临时文件后 flush + fsync 再 replace。

### D8. `vt.write()` 的 `type` 与 `tag` 参数冗余且与 WAL 冲突
- **出处**：§5.2 API 同时有 `type` 和 `tag` 两个参数；§5.3 WAL 示例把 tag 值（`"blocker"`）直接写进 `type` 字段。两个概念在存储层根本没有区分。
- **裁决**：合并为一个概念：mem 节点的类型 = `type if type is not None else tag`。两参数都保留（API 兼容规格书签名），存储层只有一个 `type` 字段（与 §5.3 WAL 示例一致）。

## B 类：欠定义（落地必须裁决）

### D9. resolve 的遍历方向未定义
- **出处**：§4.2 只说"沿关系边遍历 depth 层"。§4.1 的数据结构专门维护 `in_edges`（反向索引），暗示需要反向可达；且 `--ENFORCED-BY-->` 这类边如果只沿出边走，从 `middleware.jwt_verify` 永远查不到它执行的规则，检索价值减半。
- **裁决**：**双向 BFS**（出边 + 入边），这是 `in_edges` 存在的唯一合理解释。方向信息保留在边上（供 include_edges 输出与未来过滤），可达性不区分方向。

### D10. `type_filter` 语义二义（过滤输出 vs 剪枝遍历）
- **出处**：§4.2 只说"只返回约束节点"（示例参数 `["RULE", "RULE"]` 本身还是个笔误）。若在遍历时剪枝，`RULE—DESC—RULE` 的中间节点被滤掉会切断连通性，结果随图形状不可预测。
- **裁决**：`type_filter` **只过滤输出，不影响遍历**；根节点豁免（显式请求的节点永远完整返回）。过滤粒度是 part（facet）级：只输出类型命中的行。

### D11. TIR 输出顺序 / 确定性规则缺失
- **出处**：§4.2 承诺"相同图状态 + 相同参数 → 相同结果"，但没有给排序规则。
- **裁决**：固定为：BFS 发现序（根最先）；同层邻居按"出边声明序，再入边声明序"；每节点只输出一次；节点内 parts 按文件行序。图加载顺序确定 → 全链路确定。

### D12. 悬空引用是 Phase 1 的常态，但 resolve 行为未定义
- **出处**：§3.2 规格书自己的示例文件里**所有** REF 目标（`middleware.jwt_verify`、`db.user_table`、`api.endpoint.login`）都在文件外；跨文件合并却推迟到 P4.4。默认 compile 允许悬空（§8.2 只有 --strict 才报错），那 resolve 撞到不存在的目标节点怎么办，规格没说。
- **裁决**：三层策略：
  1. resolve 遍历时**静默跳过**图中不存在的目标（不报错、不输出占位符）；
  2. `vt check` 默认把悬空引用列为 warning，`--strict` 升级为 error（照规格）；
  3. **提前实现多 .vtg 合并加载**（跨文件节点 ID 冲突 → 报错），否则规格书自己的示例文档都无法完整检索。P4.4 剩下的部分（合并策略、增量合并）仍留待后续。

### D13. mem→doc 跨图边未定义
- **出处**：§5.2 `edges: list[str]` 没说目标能不能是 doc 节点（如 `auth.sec_1`）。而"会话记忆锚定到知识库节点"恰恰是这套双图设计最有价值的用法。
- **裁决**：**允许 mem→doc 单向引用**（doc→mem 不可能：编译期 mem ID 尚不存在，天然无环）。`UnifiedStore` 同时持有 doc 图与 mem 图，resolve 跨图遍历；mem 图的入边索引可以给 doc 节点建反向索引（doc 图本身只读，不被污染）。

### D14. `_next_seq` 的崩溃恢复策略未定义
- **出处**：§4.1 有 `_next_seq` 字段，§5.4 恢复流程完全没提它。若恢复后从错误位置续编或复用已删除 ID，旧引用会指向新内容（悬空引用变成错误引用，更危险）。
- **裁决**：快照落盘 `next_seq`；WAL 重放时对每条 write/delete 记录做 `next_seq = max(next_seq, id+1)`；**ID 永不复用**（删除不回收序号）。

### D15. checkpoint 与并发写在单一 WAL 文件上的竞态
- **出处**：§5.1 "清除已快照的 WAL 记录"没有给出与持续追加写并发时的安全顺序。
- **裁决**：锁内按固定顺序执行：序列化快照 → fsync → `os.replace` 生效 → **截断 WAL** → 追加 checkpoint 标记。配合"重放幂等"（D4），任何一步之间崩溃都安全：
  - 快照生效前崩溃 → 老 WAL 全量重放；
  - 快照生效后、截断前崩溃 → WAL 记录与快照重叠，重放为幂等覆盖；
  - 截断后崩溃 → WAL 只剩 checkpoint 标记，重放为空。

### D16. `%id` 与节点命名空间的关系未定义
- **出处**：示例文件 `%id system/auth`，节点却叫 `auth.*`，两者之间没有任何规则关联；跨文件 ID 冲突（两个文件都定义 `auth.overview`）在 P4 之前无人负责。
- **裁决**：Phase 1 不强制关联（规格未定义就不发明强约束）；多文件合并加载时做全局 ID 冲突检测（冲突 → 报错并指出两个来源文件）。另见 D19 的 `%ns` 提案。

### D17. TIR 前缀遇到 mem ID 会产生 `[##001]`
- **出处**：§4.3 前缀格式 `[#<node_id>:<type>]`，而 mem 节点 ID 本身就带 `#`（`#001`），机械拼接得到 `[##001:...]`。
- **裁决**：前缀吸收 ID 自带的 `#`：doc → `[#auth.sec_1:RULE]`，mem → `[#001:blocker]` / `[#001]`。两类 ID 形状（含点的标识符 vs 纯数字）仍可区分。

### D18. Schema 文件查找规则未明说 + 其余小项
- `%schema project_x` → 查找 .vt 文件**同目录**下的 `project_x.vtschema`；文件头声明的名称必须与请求名一致，否则 `schema_name_mismatch`。
- 注释判定：`//` 仅在**行首**（去除缩进后）生效；行内 `//` 属于内容（否则 `SRC` 节点里的 URL 会被截断）。
- 指令区边界：`%` 指令必须出现在首个内容行之前，之后出现 → `directive_after_body` 错误。
- `%vt` 必须是物理第一行（照规格），版本号格式 `\d+\.\d+(\.\d+)?`。

## C 类：战略风险（不改架构，但必须警惕）

### D19. §3.4 的 token 对比表是"斜的"——真正的成本大头是每行重复的语义 ID
- Markdown 对照组用了 `- **加粗**` 装饰（没人这么写朴素规则列表），抬高了对照组；
- 更关键：`auth.sec_1` 这类语义 ID 在 cl100k 下约 4–6 token，**每行重复**。对一条 10 token 的内容行，ID 开销就是 40–60%，远超类型符（1 token）的贡献。".vt 结构开销 ≤ 15%"的宣称在带命名空间前缀的真实 ID 下大概率不成立；
- .vt 的真实优势来源是**读取侧少注入**（目标 B），不是"写入侧语法便宜"（目标 A）。P2.1 若用朴素 Markdown 对照 + 把 ID 计入结构开销，结论可能触发红线。
- **缓解（v0.3.2 提案，已实现，opt-in）**：新增 `%ns <prefix>` 文件头指令：声明后，行内不含 `.` 的裸 ID 在解析期自动展开为 `<prefix>.<id>`（节点 ID 与 REF 端点同规则），把每行 ID 成本砍掉一半以上。不声明 `%ns` 时行为与规格完全一致。
- **P2.1 方法论修正**：对照组必须是朴素 Markdown（无加粗）；.vt 组分别测"无 %ns / 有 %ns"两档；结构开销的分母口径（纯内容 token）必须先钉死。

### D20. 冷启动问题：P1 阶段 Agent 从哪拿到第一个节点 ID？
- `vt.search()` 在 Phase 3，`resolve` 需要已知起点。规格没有给 P1 的入口方案。
- **缓解**：提供 `toc()`（全部 DEF 节点的 TIR 输出）作为廉价入口索引——注入一次目录，Agent 从中选起点再 resolve。`vt stats` CLI 同时输出类型计数与 DEF 目录。

### D21. TIR 丢弃了边：关系语义永远到不了 LLM
- §4.3 的 TIR 只有节点行，没有边行。`--ENFORCED-BY-->` 等关系类型只用于**检索选择**，LLM 看不到"谁强制执行谁"。这是一个成立的设计（边=检索索引），但规格没有承认这个后果。
- **缓解**：`resolve(..., include_edges=True)` 可选输出边行（格式 `[#a] --REL--> [#b]`，不复用 .vt 语法，维持 §12 的"TIR 不含 .vt 语法字符"验收）。默认关闭，遵规格。

### D22. 含 fsync 的 P99 < 5ms 在 Windows / 杀毒软件环境不保险
- `FlushFileBuffers` 在消费级 SSD + Defender 实时扫描下尾延迟可能超标。已通过 D3 的 durability 参数化留出退路；P2.4 用实测数据说话，不预设结论。

## 结论

- A 类 8 项全部有明确裁决并已在实现中修复；
- B 类 10 项全部钉死语义，记录于 `DECISIONS.md`；
- C 类 4 项给出缓解措施（`%ns`、`toc()`、`include_edges`、durability 参数化），并修正了 P2 的测试方法论；
- 架构主干（双模式 / 三层 IR / WAL+快照 / 双指针热加载）经审查成立，未做结构性推翻。
