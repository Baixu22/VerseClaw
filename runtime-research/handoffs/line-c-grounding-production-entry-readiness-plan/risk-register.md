# Line C Grounding Production-entry Risk Register

This register is scoped to production-entry readiness planning. It does not authorize implementation.

| Risk | Production-entry concern | Required mitigation | Validation evidence | Stop condition |
| --- | --- | --- | --- | --- |
| Default-on drift | Internal diagnostics could become silently enabled by config, defaults, package scripts, or rollout language. | Keep every phase explicit/default-off; require fresh specs for opt-in and default-on proposal; scan for default-on claims. | Spec validation, default-off parity tests, README review, boundary scans. | Any default-on behavior or production-default claim appears. |
| Runtime authority drift | Diagnostics metadata could be interpreted as runtime, completion, provider, tool, security, approval, retry, or Gateway authority. | Preserve `authority: "none"` and non-authoritative wording; forbid runtime decision coupling. | Authority sentinel tests, no-authority marker checks, synthesis audits. | Any diagnostics output changes runtime decisions or claims authority. |
| Prompt/model-message injection | Grounding summaries could enter prompts, model messages, reviewer prompts, user/system prompts, or provider payloads. | Forbid prompt/model-message assembly until a later accepted spec; scan prompt and provider surfaces if touched. | Boundary scans; default prompt parity tests in future phases. | Any grounding text enters prompt/model-message/provider transport. |
| Provider ordering drift | Diagnostics could influence registry order, provider ranking, default registration, or provider selection. | Require provider ordering diff count 0 unless a future spec explicitly accepts a change. | Context provider registry tests; provider ordering snapshots. | Any provider order, ranking, selection, or default registration changes. |
| Memory promotion/fact acceptance/episode write | Grounding could be treated as durable facts, memory promotions, invalidation acceptance, or episode writes. | Forbid memory promotion, fact acceptance, episode write, memory store writes, and durable fact authority. | Memory-provider tests; promotion/write boundary scans. | Any grounding material creates or approves durable memory state. |
| Persistence/database/sidecar/cache creep | Planning could accidentally add SQLite/JSONL/sidecar/cache/exporter/listener/service surfaces. | Keep this phase docs/spec-only; future phases need explicit persistence rejection or fresh accepted persistence spec. | Service/database scan over touched files; rollback no-residue review. | Any new runtime state file, DB schema, cache, service, listener, exporter, or daemon appears. |
| Raw prompt/trace/payload leakage | Raw prompts, traces, full payloads, tool args/output, stdout/stderr, env, secrets, API keys, auth headers, traceparent, tracestate, or baggage could be retained or displayed. | Summary-only diagnostics; raw sentinel tests; redaction/display plan before any operator presentation. | Authority effectiveness metrics; raw-retention scans; redaction tests in future presentation phase. | Any raw or secret-like value is emitted, stored, or displayed. |
| Untrusted refs leakage | Untrusted refs could be included in summaries, prompts, provider payloads, persisted records, or UI. | Force `includeUntrusted: false`; exclude untrusted refs by default; test hostile untrusted metadata. | `includeUntrustedForcedFalseRate = 1`; untrusted ref exclusion tests. | Any untrusted ref appears in emitted diagnostics or downstream surfaces. |
| Budget/token/performance regressions | Diagnostics could add token, latency, or memory overhead that is acceptable in tests but unsafe in production. | Bound summary count/size; track p95 overhead, token delta, sample volume, and budget exhaustion behavior. | Existing budget tests; future production-like replay metrics. | Budget breach, unbounded output, or unacceptable p95 overhead. |
| Renderer/Main/Gateway/host-api/api-client boundary violation | Future presentation or opt-in work could bypass Main-owned transport policy or add renderer direct IPC/Gateway calls. | Renderer must use host-api/api-client; no direct Gateway HTTP/WebSocket; comms replay/compare when comms paths are touched. | Boundary scans; comms replay/compare for touched comms paths; E2E if UI exists. | Direct renderer IPC/Gateway call, renderer-owned transport switching, or unvalidated comms path change. |
| UI/docs/i18n mismatch | Operator or user-facing presentation could ship without locale coverage, E2E, or accurate docs. | No UI in this phase; future UI requires en/zh/ja/ru i18n, design tokens, and Electron E2E. | README review now; locale and E2E checks in future UI phase. | User-visible text without locale coverage, missing E2E, or docs that imply unsupported authority. |
| Rollback failure | Production opt-in could lack a fast path back to diagnostics-only or disabled behavior. | Every phase must define gate closure, rollback owner, no-residue proof, and stop conditions. | Rollback playbook; rollback drill in future opt-in phases. | Gate closure fails to restore default behavior or cleanup requires unplanned migration. |

## Residual Risk

Residual risk is acceptable only for planning-complete status. It is not acceptable for production rollout, runtime authority, default-on behavior, prompt/model-message use, provider ordering changes, memory promotion, persistence, or UI cutover.
