## Optimization Implemented

This round adds an opt-in signal-quality optimization and a sanitized projection boundary to the collector:

- Default collector order is unchanged.
- Callers may pass `prioritize: true` to keep high-value diagnostic reasons before low-value `registered` / `legacy_authoritative` diagnostics under tight limits.
- Collector output now includes `omittedSummary`, breaking omitted diagnostics down by count, context/tool surface, status, and reason.
- The prioritization comparator is reason-first, status-second. This matters because a high-value reason such as `runtime_unavailable` can otherwise be hidden behind lower-value diagnostics that happen to carry a stronger status.
- Callers may pass `sanitize: true` to receive diagnostics-only projected output that redacts diagnostic `message`, diagnostic `metadata`, evidence ref identity text, evidence summaries, evidence metadata, and unsafe provider ids.
- TaskLoop registry shadow now consumes sanitized diagnostics only. Raw producer diagnostic payloads remain available only to trusted in-memory callers/tests and are not written into shadow event metadata or evidence refs.
- `collectRuntimeRegistryDiagnosticsForControlledConsumer()` is now the approved internal consumer entry. It requires explicit `enabled: true` plus all Registry flags, forces `sanitize: true` and `prioritize: true`, reports `gateStatus` and `blockedReasons`, and remains diagnostics-only/in-memory/non-authoritative.
- Missing consumer enablement or any required Registry flag fail-closes with included diagnostic count 0 while preserving omitted diagnostic counts.

## Design Judgment

The current design is computationally safe and stable for a diagnostics-only internal consumer. The controlled entry itself is not the bottleneck: real producer repeat runs measured controlled consumer latency at 0.764ms P95, and a 1024-diagnostic real-producer pressure input measured 4.260ms for the controlled sanitized/prioritized path in this test environment.

The bottleneck is upstream representativeness and operator contract maturity:

- Producer coverage is heavily tool-provider weighted: 25 tool diagnostics, 4 context diagnostics, and 2 TaskLoop shadow diagnostics per run.
- TaskLoop remains only an injected sanitized shadow metadata path, which is correct for authority safety but too narrow to justify default-on or task-completion use.
- Actionability is proven by classification and zero noise in this corpus, but not yet by live operator decisions over varied real sessions.
- The design has no approved retention, privacy, UI, or public configuration contract, which is appropriate now but blocks production-facing default behavior.

Conclusion: the route is ready for real internal opt-in diagnostic work through the controlled entry. Continue tightening through repeated-session corpus and operator contract evidence before any expansion. Do not promote to default-on, persistence, UI, provider ordering authority, TaskLoop authority, Gateway/provider transport changes, or completion evidence.

## Post-Optimization Plan

1. Use `collectRuntimeRegistryDiagnosticsForControlledConsumer()` as the only internal consumer entry for real work.
2. Keep raw diagnostics only in test-owned memory and raw leakage tests; raw collector output is a detector baseline, not an operator-facing contract.
3. Preserve mandatory sanitized/prioritized output at the controlled entry.
4. Extend producer coverage before any expansion: context and TaskLoop currently remain underrepresented relative to tool/MCP diagnostics.
5. Add live operator contract evidence before any default behavior: decisions, privacy/retention policy, and UI or API presentation rules are still undefined.
