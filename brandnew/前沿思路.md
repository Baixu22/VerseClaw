# 真正意义上的 Runtime 重构：六个原创产品级设计

## 一、Sovereignty Kernel：可验证执行的不可篡改内核

这是 2026 年最重要的 runtime 级别概念，没有任何成熟框架实现了它。

### 核心问题

这是核心设计前提：LLM 驱动的 agent 是不确定的、不可形式化验证的，可能产生任意输出。

内核记录的是 agent 声称做了什么，不一定是在外部世界实际发生了什么。对于 execute 动作类型，actor 在外部执行并提交结构化 payload（输入/输出 OID、退出码、artifact hash）。内核验证 payload 格式和 OID 语法，但不验证 OID 引用是否指向真实内容，或声明的结果是否与实际执行结果对应。

**这意味着你现有的 Observability 记录的是 agent 自己汇报的内容，不是真实发生的内容。**

### 三权分离：授权意图 / 隔离执行 / 验证副作用

MCP 授权意图，沙箱约束执行，OS 级别可观测性验证副作用。每一层都是必要的，没有一层是充分的。实际模型是它们的分离：授权意图（harness 拥有）→ 隔离执行（所有权有争议）→ 验证副作用（必须由平台拥有）。

### Sovereignty Kernel 的实现

```
你的 runtime 当前只有第一层（授权意图）。
需要新增第三层（验证副作用）作为独立内核。
```

```typescript
// sovereignty-kernel/kernel.ts
// 基于 arxiv:2602.20214 (PunkGo) 的工程化实现
// 用 Rust 编写核心管道，Node.js 通过 FFI 调用

// 核心设计：append-only 不可篡改执行日志
// 每一个 agent 动作产生一个带密码学证明的事件

interface SovereigntyKernel {
  
  // ===== 核心：行动记录（不是 agent 自己汇报，是内核观测）=====
  
  // 拦截 tool 执行的 OS 级别事件
  // 不依赖 agent 汇报，直接观测系统调用
  observeExecution(
    toolCallId: string,
    // 从 OS 层面观测到的实际副作用
    sideEffects: {
      filesModified: string[];      // 实际被写的文件（inotify 观测）
      networkCalls: NetworkCall[];  // 实际的网络请求（eBPF 观测）
      processSpawned: Process[];    // 实际 spawn 的子进程
      memoryDelta: MemoryDelta;     // 实际内存变化
    }
  ): ObservationRecord;
  
  // 将观测结果与 agent 声明做交叉验证
  crossValidate(
    agentClaim: ToolResult,           // agent 汇报的结果
    observation: ObservationRecord    // 内核实际观测的
  ): ValidationResult {
    
    // 文件变更交叉验证
    const fileMismatch = this.diffFileSets(
      agentClaim.filesChanged,
      observation.sideEffects.filesModified
    );
    
    // 网络调用交叉验证
    const networkMismatch = this.diffNetworkCalls(
      agentClaim.apiCalls,
      observation.sideEffects.networkCalls
    );
    
    if (fileMismatch.hasDiscrepancy || networkMismatch.hasDiscrepancy) {
      // 这里发现了 agent 声称做了 X 但实际做了 Y 的情况
      // 这是现有 Observability 完全无法检测的
      return {
        valid: false,
        discrepancies: [fileMismatch, networkMismatch],
        severity: this.assessSeverity(fileMismatch, networkMismatch),
      };
    }
    
    return { valid: true };
  },
  
  // 不可篡改的 append-only 执行日志
  // 每条记录包含密码学哈希链
  appendToLog(
    record: ExecutionRecord,
    previousHash: string
  ): LogEntry {
    const entry: LogEntry = {
      ...record,
      previousHash,                    // 哈希链（类似区块链原理）
      timestamp: Date.now(),
      hash: this.sha256(record, previousHash),
    };
    
    this.log.append(entry);
    return entry;
  },
  
  // 为外部审计生成可验证的执行证明
  generateExecutionProof(
    sessionKey: string,
    timeRange: TimeRange
  ): ExecutionProof {
    // 基于哈希链，任何篡改都可被检测
    // 支持 EU AI Act Article 12 的合规要求
  }
}
```

## 二、eBPF Intent-Driven Resource Controller：OS 级别的工具调用感知资源控制

这是 2026 年最重要的系统级论文之一，已开源。

### 核心发现

将 agent 工作负载特征与 serverless、微服务和批处理工作负载对比，发现三个不匹配：粒度不匹配（容器级策略 vs 工具调用级动态）、响应性不匹配（用户空间反应 vs 亚秒级不可预测突发）、适应性不匹配（基于历史的预测 vs 非确定性有状态执行）。

AgentCgroup 提出了一个意图驱动的 eBPF 资源控制器，利用 agent 声明资源需求和重构执行策略的能力，使用与工具调用边界对齐的分层 cgroup v2 结构、通过 sched_ext 和 memcg_bpf_ops 的内核内执行，以及运行时自适应策略。初步评估显示多租户隔离改善和资源浪费减少。

### 对你的系统的意义

你当前的沙箱是 `policy-light`（进程级别），或者 Docker（容器级别）。两者都存在根本性的粒度问题：

AI agent 在运行时生成并执行未知代码。你字面上不知道它下一步会做什么。攻击面从根本上更大。

eBPF 方案将资源控制粒度从"容器级别"下沉到"单次工具调用级别"：

```typescript
// ebpf-controller/intent-controller.ts
// 包装 AgentCgroup 的 Node.js 绑定

interface IntentDrivenController {
  
  // 在每次工具调用开始前声明资源意图
  // agent 自己声明它需要什么资源
  declareIntent(
    toolCallId: string,
    toolName: string,
    estimatedResources: ResourceIntent
  ): CgroupConfig {
    
    // 根据工具类型和角色契约，动态设置 cgroup 约束
    const limits = this.deriveLimits(toolName, estimatedResources);
    
    // 在 cgroup v2 中为这次工具调用创建独立的控制组
    return this.cgroupManager.create({
      id: `tool-call-${toolCallId}`,
      
      // 内存限制：不同工具不同限制
      memory: {
        limit: limits.memoryBytes,
        // 优雅降级：超限时不直接 OOM kill，而是通知 runtime
        softLimit: limits.memoryBytes * 0.8,
        onExceed: 'notify-runtime',
      },
      
      // CPU 限制：与 effort 等级对应
      cpu: {
        weight: this.effortToCpuWeight(estimatedResources.effort),
        // 防止单次工具调用独占 CPU
        maxPeriodUs: 100_000,
        maxQuotaUs: limits.cpuQuota,
      },
      
      // I/O 限制：防止大文件读写拖垮整个系统
      blkio: {
        readBps: limits.diskReadBps,
        writeBps: limits.diskWriteBps,
      },
      
      // 网络限制（通过 eBPF tc 实现）
      network: {
        egressBps: limits.networkEgressBps,
        allowedHosts: this.deriveAllowedHosts(toolName),
      },
    });
  },
  
  // 运行时自适应：基于实际观测调整策略
  adaptPolicy(
    toolCallId: string,
    observation: ResourceObservation
  ): void {
    
    // 如果 agent 声明的资源意图和实际使用差距很大
    // → 调整下次同类工具调用的资源配额
    const drift = this.measureDrift(
      this.declaredIntents.get(toolCallId),
      observation
    );
    
    if (drift > DRIFT_THRESHOLD) {
      this.policyStore.update(
        toolCallId.toolName,
        this.deriveNewPolicy(observation)
      );
    }
  }
}
```

## 三、SWE-Pruner：Coding Agent 专属的自适应上下文裁剪引擎

这是直接针对你核心场景（coding agent）的 runtime 重构，有最新的学术数据支撑。

### 核心数据

在实践中，coding agent 在反复探索代码库上耗费了大量 token 预算。对 Mini SWE Agent 使用 Claude Sonnet 4.5 在 SWE-Bench Verified 上的轨迹分析显示：读操作占 token 消耗的 76.1%，这说明了对上下文裁剪机制的需求。

关系不是线性的——2 倍 turn 数可能导致 3-4 倍成本。一个运行 2 倍 turn 的 session 可能贵 3-4 倍。

上下文漂移在到达上下文限制之前就让 agent 崩溃。2025 年 65% 的企业 AI 失败归因于多步推理中的上下文漂移或记忆丢失，而非原始上下文耗尽。

### 五阶段自适应裁剪管线

在 ReAct 循环中，工具观察（如文件内容和命令输出）快速积累并主导上下文窗口，频繁消耗 70-80% 的可用 token 预算。标准系统依赖二进制紧急压缩阈值（通常在 95-99% 容量时触发），执行对话历史的有损摘要，导致激活过晚、严重信息损失和后续压缩的错误复合。Adaptive Context Compaction 通过五阶段渐进式压缩策略解决这个问题。

```typescript
// context-engine/swe-pruner.ts
// 专为 coding agent 设计的上下文裁剪引擎
// 不是通用压缩，而是代码感知的精准裁剪

interface SWEPruner {
  
  // ===== 核心：五阶段渐进式裁剪 =====
  
  prune(
    context: AgentContext,
    currentTokens: number,
    budget: TokenBudget
  ): PrunedContext {
    
    const pressure = currentTokens / budget.total;
    
    // Stage 1: 工具输出去重（压力 > 50%）
    // 最常见的浪费：同一个文件被读了多次
    if (pressure > 0.5) {
      context = this.deduplicateToolOutputs(context);
    }
    
    // Stage 2: 文件内容 Diff 压缩（压力 > 65%）
    // 对同一文件的多次读取，只保留 diff
    if (pressure > 0.65) {
      context = this.compressFileReadHistory(context);
    }
    
    // Stage 3: 符号感知截断（压力 > 75%）
    // 不是简单截断，而是保留语义完整的代码块
    if (pressure > 0.75) {
      context = this.symbolAwareTruncation(context);
    }
    
    // Stage 4: 任务相关性过滤（压力 > 85%）
    // 通过项目地图判断哪些内容与当前任务相关
    if (pressure > 0.85) {
      context = this.taskRelevanceFilter(context, this.projectMap);
    }
    
    // Stage 5: 结构化摘要（压力 > 92%）
    // 最后手段：生成结构化摘要，但保留关键事实
    if (pressure > 0.92) {
      context = this.structuredSummary(context);
    }
    
    return context;
  },
  
  // ===== 关键：符号感知截断（Stage 3 的核心）=====
  // 不能在函数中间截断，必须在语义边界处截断
  
  symbolAwareTruncation(context: AgentContext): AgentContext {
    
    const fileContents = context.toolResults
      .filter(r => r.toolName === 'read_file');
    
    for (const fileResult of fileContents) {
      if (fileResult.tokenCount > SINGLE_FILE_BUDGET) {
        
        // 用 AST 解析，找到语义边界
        const ast = this.parseAST(fileResult.content, fileResult.language);
        
        // 只保留与当前任务相关的函数/类
        const relevantNodes = ast.findRelevant(
          this.currentTaskContext.targetSymbols
        );
        
        fileResult.content = this.extractNodes(ast, relevantNodes);
        fileResult.truncated = true;
        fileResult.truncationNote = `[Showing ${relevantNodes.length} relevant symbols. Full file available via project map.]`;
      }
    }
    
    return context;
  },
  
  // ===== KV Cache 感知压缩（不破坏稳定前缀）=====
  
  compressKVCacheAware(context: AgentContext): AgentContext {
    
    // 关键：只压缩 dynamic suffix，不动 stable prefix
    // 因为改变 stable prefix 会触发完整的 KV cache 缺失
    // 导致 provider 端重新计算整个前缀
    
    const stablePrefix = this.extractStablePrefix(context);
    const dynamicSuffix = this.extractDynamicSuffix(context);
    
    const compressedSuffix = this.compress(dynamicSuffix);
    
    return this.reassemble(stablePrefix, compressedSuffix);
    // stablePrefix 的 token 边界完全不变 → KV cache 100% 命中
  },
  
  // ===== 预算感知三态管理 =====
  // 基于 ContextBudget 论文 (arxiv:2604.01664)
  
  budgetAwareStrategy(
    currentBudget: number,
    totalBudget: number
  ): CompressionStrategy {
    
    const ratio = currentBudget / totalBudget;
    
    if (ratio > 0.6) {
      // 高预算：保留完整历史，不压缩
      return { mode: 'preserve', deferCompression: true };
    }
    
    if (ratio > 0.25) {
      // 中等预算：选择性聚合，压缩冗余片段
      return { mode: 'selective', targetRedundancyThreshold: 0.3 };
    }
    
    // 低预算：折叠为完整聚合表示
    return { mode: 'collapse', targetTokens: totalBudget * 0.2 };
  }
}
```

实现基础上下文压缩在不损失信息的情况下减少 60% 的上下文。Prompt caching 为缓存的 token 提供 10 倍成本降低。

**这意味着 SWE-Pruner + KV cache 感知压缩组合，可以带来实际 5-8 倍的成本降低。** 这是真实的数字，不是理论值。

## 四、MicroKernel Agent Architecture：去中心化的 Runtime 核心

它将核心系统功能与模拟逻辑解耦，并将认知过程与物理环境和动作执行分离。因此，Agent-Kernel 实现了卓越的适应性、可配置性、可靠性和可复用性。

当前所有的 agent framework（包括 OpenClaw）都是**宏内核设计**——所有功能（routing、memory、tools、orchestration）共享一个运行时进程空间。

你的系统有 60+ 子域但它们共享同一个 Node.js 进程。

```
当前架构（宏内核）：
openclaw_runtime（单进程）
├─ agents/（全部在同一进程内）
├─ memory/（同上）
├─ skills/（同上）
├─ channels/（同上）
└─ tools/（同上）

问题：
- 一个子域的内存泄漏影响全部
- 无法独立扩展高负载子域
- 插件可以访问整个进程内存
- 更新任何子域需要重启整个 runtime
```

### MicroKernel 重构方案

```typescript
// microkernel/kernel.ts
// 最小核心：只做消息路由和进程管理
// 所有业务逻辑下沉到独立插件进程

interface AgentMicroKernel {
  
  // ===== Kernel 只做三件事 =====
  
  // 1. 消息总线（进程间通信）
  messageBus: {
    send(from: ProcessId, to: ProcessId, message: Message): void;
    broadcast(from: ProcessId, topic: string, event: Event): void;
    subscribe(processId: ProcessId, topic: string): void;
  };
  
  // 2. 进程生命周期管理
  processManager: {
    spawn(plugin: PluginManifest): ProcessHandle;
    kill(processId: ProcessId): void;
    restart(processId: ProcessId): void;
    // 健康检查
    health(processId: ProcessId): HealthStatus;
  };
  
  // 3. 最小权限分配
  capabilityManager: {
    grant(processId: ProcessId, capabilities: Capability[]): void;
    revoke(processId: ProcessId, capability: Capability): void;
    // 进程只能访问它被授权的能力
    // 不是"不鼓励"，是物理隔离
  };
}

// 每个子域变成一个独立进程（plugin）
// 通过消息总线通信，不共享内存

// memory/ 子域 → 独立 Memory Process
interface MemoryPlugin {
  // 只暴露接口，内部状态完全隔离
  search(query: string): MemoryResult[];
  propose(draft: MemoryProposalDraft): ProposalId;
  // memory 进程崩溃不影响 agents 进程
}

// agents/ 子域 → 独立 Agents Process（或多个）
interface AgentsPlugin {
  spawnRole(roleContract: RoleContract, task: Task): AgentHandle;
  // 多个 coding agent 可以在独立进程中并行
  // 互相不干扰，资源独立分配
}
```

通过将数据绑定到各自的插件，建立清晰的职责域，实现故障隔离：数据异常被限制在特定插件中，防止级联失败并显著降低调试复杂性。此外，这种隔离确保 schema 变更严格局部化，防止集中式存储设计中常见的连锁反应。

**与你现有 Plugin SDK 的融合路径**：

```
Phase 1: Kernel 抽象层（不破坏现有代码）
├─ 在 gateway/ 和 agents/ 之间引入消息总线抽象
├─ 现有子域暂时仍在同一进程（兼容）
└─ 但所有通信改为通过消息总线（为后续隔离做准备）

Phase 2: 高风险子域隔离
├─ skills/ → 独立进程（skill 代码不可信，最需要隔离）
├─ channels/ → 独立进程（外部网络接入点）
└─ mcp/ → 独立进程（第三方 MCP server）

Phase 3: 核心子域隔离
├─ memory/ → 独立进程（防止记忆投毒影响其他子域）
├─ agents/ → 多实例进程池（并行 agent 不再争抢资源）
└─ Kernel 真正精简为最小核心
```

## 五、Context Drift 检测引擎：在失败发生前预警

监控多步任务中的漂移信号：重新读取已处理的内容、重述已做的决定、目标措辞变化。

这是目前**完全没有开源实现**的一个方向。你可以率先把它产品化。

```typescript
// context-engine/drift-detector.ts
// 实时检测 agent 的推理是否已经偏离

interface ContextDriftDetector {
  
  // 监控四种漂移信号
  detectDrift(
    trajectory: AgentTrajectory,
    originalGoal: TaskGoal
  ): DriftReport {
    
    const signals: DriftSignal[] = [];
    
    // 信号 1: 重读信号（Re-read Signal）
    // agent 重新读取已经处理过的文件/符号 → 遗忘症状
    const rereadSignal = this.detectReReads(trajectory);
    if (rereadSignal.ratio > 0.2) {
      signals.push({
        type: 'amnesia',
        severity: rereadSignal.ratio,
        evidence: rereadSignal.duplicatedReads,
        remedy: 'inject-summary',  // 注入之前读取的摘要
      });
    }
    
    // 信号 2: 决策重述信号（Decision Restatement）
    // agent 重新"决定"已经决定过的事 → 循环症状
    const restatementSignal = this.detectRestatements(trajectory);
    if (restatementSignal.detected) {
      signals.push({
        type: 'loop',
        severity: restatementSignal.count,
        evidence: restatementSignal.restatedDecisions,
        remedy: 'inject-decision-log',
      });
    }
    
    // 信号 3: 目标漂移信号（Goal Drift）
    // 当前 agent 输出的目标措辞与原始任务偏离
    const goalDrift = this.measureGoalDrift(
      trajectory.recentOutputs,
      originalGoal
    );
    if (goalDrift.cosineDistance > 0.3) {
      signals.push({
        type: 'goal-drift',
        severity: goalDrift.cosineDistance,
        evidence: goalDrift.divergentStatements,
        remedy: 'steer-goal-realignment',
      });
    }
    
    // 信号 4: Token 曲线异常（Token Curve Anomaly）
    // 基于 Vantage 数据：后期 turn 成本非线性增长是失控信号
    const tokenAnomaly = this.analyzeTokenCurve(trajectory.tokenCosts);
    if (tokenAnomaly.accelerationRate > 2.5) {
      signals.push({
        type: 'token-runaway',
        severity: tokenAnomaly.accelerationRate,
        evidence: tokenAnomaly.costBreakdown,
        remedy: 'trigger-compaction',
      });
    }
    
    // 综合评分
    const overallDrift = this.aggregateSignals(signals);
    
    return {
      signals,
      overallDrift,
      // 对应的恢复动作
      recommendedAction: this.selectRemedy(overallDrift, signals),
    };
  },
  
  // 自动恢复：在 drift 导致失败之前介入
  autoRecover(
    drift: DriftReport,
    sessionKey: string
  ): RecoveryAction {
    
    switch (drift.recommendedAction) {
      
      case 'inject-summary':
        // 把之前读取过的内容的摘要注入进去
        // 复用已有的 steering 机制
        return this.steeringInjector.inject(sessionKey, {
          type: 'context-recovery',
          content: this.buildReadSummary(drift.evidence),
        });
      
      case 'inject-decision-log':
        // 注入已做决策的结构化列表
        // 让 agent "想起"它已经决定过了
        return this.steeringInjector.inject(sessionKey, {
          type: 'decision-recovery',
          content: this.buildDecisionLog(drift.evidence),
        });
      
      case 'steer-goal-realignment':
        // 注入原始目标，强制重新对齐
        return this.steeringInjector.inject(sessionKey, {
          type: 'goal-realignment',
          content: `Original task goal: ${this.originalGoal}\n` +
                   `Current trajectory appears to be drifting. ` +
                   `Please refocus on the original goal.`,
        });
      
      case 'trigger-compaction':
        // 主动触发压缩，而不是等到 95% 才触发
        // 复用已有的 sessions.compact
        return this.gateway.call('sessions.compact', { sessionKey });
    }
  }
}
```

## 六、Episodic Context Reconstruction：无损记忆重建

E-mem 引入了一个情节记忆框架，其中助手 agent 维护未压缩的记忆上下文，而主 agent 编排全局规划，用上下文重建替代破坏性的记忆压缩。

这解决了你现有 `sessions.compact` 的根本性问题：**压缩是有损的**，你永远无法从摘要中恢复原始细节。

```typescript
// memory/episodic-reconstruction.ts
// 核心思想：不压缩，而是重建
// assistant agents 保存完整的情节记忆
// master agent 只处理高层规划

interface EpisodicReconstructionEngine {
  
  // ===== 核心：情节分片存储 =====
  
  // 把对话历史按情节（episode）分片，每个情节完整存储
  storeEpisode(
    episode: ConversationEpisode,
    context: EpisodeContext
  ): EpisodeId {
    
    const episodeRecord: EpisodeRecord = {
      id: generateId(),
      
      // 完整的情节内容（不压缩！）
      turns: episode.turns,
      toolCalls: episode.toolCalls,
      toolResults: episode.toolResults,     // 原始工具结果
      fileContents: episode.fileContents,   // 原始文件内容
      
      // 情节的结构化元数据（用于检索）
      metadata: {
        startGoal: episode.goalAtStart,
        endState: episode.stateAtEnd,
        decisionsMAde: episode.decisions,
        filesModified: episode.filesModified,
        symbolsAccessed: episode.symbolsAccessed,
        // 意图索引：用于后续按意图检索
        intentCues: this.extractIntentCues(episode),
      },
      
      // 关联到已有的 trajectory.jsonl
      trajectoryRef: context.trajectoryPath,
    };
    
    // 存入独立的情节存储（不是全局 memory）
    return this.episodeStore.save(episodeRecord);
  },
  
  // ===== 按意图重建上下文（不是检索摘要）=====
  
  reconstruct(
    currentTask: Task,
    budget: number
  ): ReconstructedContext {
    
    // 1. 用意图向量找相关情节
    const relevantEpisodes = this.findByIntent(
      currentTask,
      this.episodeStore
    );
    
    // 2. 关键：直接重建原始上下文片段，不是摘要
    // 只要 budget 允许，就用原始内容
    const reconstructed: ReconstructedContext = {
      episodes: [],
      totalTokens: 0,
    };
    
    for (const episode of relevantEpisodes) {
      
      // 按相关性选择情节中最相关的 turns
      const relevantTurns = episode.turns.filter(
        turn => this.isRelevant(turn, currentTask)
      );
      
      const episodeTokens = this.countTokens(relevantTurns);
      
      if (reconstructed.totalTokens + episodeTokens <= budget) {
        // Budget 允许 → 原始内容，无损
        reconstructed.episodes.push({
          episode,
          content: relevantTurns,
          mode: 'full',
        });
      } else {
        // Budget 紧张 → 只加入情节摘要（元数据级别）
        reconstructed.episodes.push({
          episode,
          content: episode.metadata,
          mode: 'summary',
        });
      }
      
      reconstructed.totalTokens += episodeTokens;
      if (reconstructed.totalTokens >= budget) break;
    }
    
    return reconstructed;
  }
}
```

**与你已有系统的融合**：

```

新增的 EpisodicReconstruction → 主要路径（无损重建）

已有的 role-memory.sqlite → 存储角色级别的治理知识

已有的 sessions.fork → 可以 fork 到新 session，带情节库

```

## 一、执行模型的根本性问题：顺序瓶颈

2026 年生产 AI agent 系统的主要瓶颈不再是模型推理速度，而是顺序工具执行。一个 agent 依次进行五次工具调用、每次等待前一次完成，就要承受每次调用的累积延迟。

你的 runtime 当前的 agentic loop 是：

```
model call → tool_1 → wait → tool_2 → wait → tool_3 → wait → response
```

这在代码任务中尤为严重，因为一个典型的 coding turn 可能包含：read file → analyze → search symbol → read another file → write file，全部串行。

跨框架的基准测试显示，当 agent 并发调度独立工作时，可以实现一致的 1.8x–3.7x 挂钟时间加速和高达 6x 的成本降低。

## 二、六个真正的 Runtime 层优化方向

### 方向 1：投机执行引擎（Speculative Tool Execution）

这是 2026 年最前沿的 runtime 级优化，直接针对顺序瓶颈。

PASTE 的核心洞察是 agent 的工具调用序列不是随机的——它们遵循重复出现的模式。一个查找用户资料的 agent 几乎总是会接着检查权限。一个读取文件的 coding agent 通常会随后编辑它。

**工作原理**：

一个投机模式 P = (C, T, f, p) 由以下部分组成：上下文 C（之前事件元数据的有序子序列）；工具类型 T（预测的下一个工具）；参数函数 f（从之前的工具输出或提示中推导预测参数）；优先级 p（平衡预测可能性、延迟节省和资源成本的效用分数）。

投机任务在闲置资源上贪婪运行。当存在竞争时，低效用的投机任务会被抢占以优先处理真实调用。

**对你的系统的意义**：

你已有 `trajectory.jsonl` 记录每个会话的工具调用轨迹。这就是**天然的模式训练数据**。不需要外部基础设施，直接从已有的 trajectory 文件中挖掘模式：

```typescript
// speculative/pattern-miner.ts
// 直接消费已有的 trajectory.jsonl

interface SpeculativePatternMiner {
  
  // 从 trajectory.jsonl 中挖掘工具调用序列模式
  minePatterns(trajectoryPath: string): SpeculativePattern[];
  
  // 模式结构（对齐 PASTE 的形式化定义）
  // P = (C, T, f, p)
}

interface SpeculativePattern {
  context: ToolCallContext[];   // 触发条件（之前调用了什么）
  predictedTool: string;        // 预测下一个调用的工具
  argDerivation: string;        // 参数如何从之前的结果推导
  priority: number;             // 成功率 × 延迟节省 / 资源成本
  
  // coding agent 特有
  codeContext?: {
    filePattern?: string;       // e.g., "读完 .ts 文件后通常会 search symbol"
    taskPhase?: RolePhase;      // 在 implement 阶段的模式 vs review 阶段
  };
}
```

PASTE 足够轻量，可以作为 sidecar 部署在现有 agent runtime 旁边，在不需要专用基础设施或对执行栈进行颠覆性改变的情况下实现延迟提升。模式预测和调度策略的总体延迟开销低于 100ms。

**与你架构的精确对接**：

```
当前的 Lane Queue（串行执行防竞态）
    ↓
可以改造为：Lane Queue + Speculative Sidecar
    ├─ 主 lane：真实工具调用（串行保证不变）
    └─ 投机 lane：基于模式预测的提前执行
       ├─ 命中 → promote（直接复用结果）
       └─ 未命中 → discard（回滚，代价可控）
```

### 方向 2：上下文工程引擎（Context Engineering Engine）

这是被严重低估的 runtime 层优化。

上下文工程是决定什么内容进入上下文窗口、以什么顺序排列、以及如何缓存和压缩以最小化预填充计算而不损害输出质量的实践。它不同于提示工程（关注指令质量），也不同于 RAG（关注检索）。提示工程优化质量，上下文工程优化成本和延迟。

你的系统当前有 `LoopContextPack` 和 `buildContextPack` 的 7 桶 token 受限设计，但这是**语义层面**的上下文管理。真正的 runtime 层上下文工程还差一个维度：**KV Cache 感知**。

普通的上下文管理系统在执行文本截断或压缩时会改变输入边界，无意中触发严重的后端 KV 缓存缺失。

这意味着你现有的 `sessions.compactionStatus/compact` 机制，每次压缩都可能在 provider 侧触发全量重新计算。

**解决方案——Cache-Aware Context Manager**：

```typescript
// context-engine/cache-aware-manager.ts
// 这是对你已有 context-engine/ 子域的 runtime 层扩展

interface CacheAwareContextManager {
  
  // 核心原则：context 的稳定前缀不能被改变
  // 稳定区（永不变动，最大化 KV cache 命中）
  stablePrefix: {
    systemPrompt: string;      // role contract prompt
    toolDefinitions: string;   // 工具定义（按字母排序，保证稳定性）
    projectMapSummary: string; // 项目地图摘要（定期更新，但版本稳定）
  };
  
  // 动态区（允许变动，但要在稳定前缀之后）
  dynamicSuffix: {
    conversationHistory: Message[];
    toolResults: ToolResult[];
    currentTask: string;
  };
  
  // 关键方法：压缩时不改变稳定前缀的 token 边界
  compactSafely(
    context: AgentContext,
    targetTokens: number
  ): SafeCompactionResult {
    // 只压缩 dynamicSuffix，不动 stablePrefix
    // 这保证了 KV cache 命中率
  };
  
  // 预算感知分配
  allocateBudget(
    totalBudget: number,
    roleContract: RoleContract
  ): BudgetAllocation {
    return {
      stablePrefix: Math.min(totalBudget * 0.4, this.stablePrefix.tokenCount),
      toolResults: totalBudget * 0.3,
      history: totalBudget * 0.2,
      reserved: totalBudget * 0.1,  // 留给输出
    };
  }
}
```

在 100:1 的输入输出比率下，预填充计算占每次请求总 GPU 时间的 85-95%。90% 的 KV 缓存命中率意味着服务器跳过 90% 的预填充工作，将每次请求的有效计算成本降低 80-90%。

对你的系统来说，**这不只是性能优化，也是成本优化**——每次 compaction 破坏 KV cache，实际上你在为同样的 stable prefix 重复付费。

### 方向 3：Skill 运行时的根本性重构

你的 skill 系统目前是**加载型**的——skill 被安装、被调用。但 2026 年的研究方向是把 skill 变成**可调度的运行时单元**。

Skill 的可组合性意味着它不仅仅是供模型消费的文档，而是 agent 架构内部的一个可调度运行时单元。更重要的是，组合不只是多个程序片段的拼接，而是程序性专长本身的高层复用。

Skill 工程引入了一种高阶抽象。一个 skill 是一个可以包含指令、工作流指导、可执行脚本、参考文档和元数据的包，所有内容都被组织为在相关时动态加载。关键洞察是：许多真实世界的任务不需要单次工具调用，而是需要由领域特定程序性知识指导的协调决策序列。

**当前 OpenClaw skill 系统的根本性问题**：

其市场采用"安装即运行"的信任模型：开发者通过 web 界面或 CLI 发现 skill，用一条命令安装，skill 以 agent 的完整系统权限执行。发布时不需要正式审查、签名或能力声明。

这不只是安全问题，也是**架构问题**：skill 和 tool 在执行层面没有本质区别，skill 的"程序性知识"优势没有在 runtime 层体现出来。

**真正的 Skill Runtime 应该是什么样的**：

```typescript
// skills/skill-runtime.ts
// 重构 skill 从"加载型"到"可调度运行时单元"

// 当前：skill 是一个工具集合
// 目标：skill 是一个有状态的、可组合的、可调度的执行单元

interface SkillRuntimeUnit {
  
  // === Skill 作为运行时单元的核心属性 ===
  
  // 1. 能力声明（不是安装时静态配置，是运行时动态查询）
  capabilities: {
    declare(): CapabilityManifest;      // 我能做什么
    requires(): CapabilityRequirement[]; // 我需要什么
    conflicts(): string[];               // 我和谁不兼容
  };
  
  // 2. 状态边界（skill 有自己的状态，不污染全局状态）
  state: {
    // skill 私有状态（不写入 agent 全局记忆）
    privateState: SkillLocalState;
    // skill 可以向外暴露的状态（需显式声明）
    publicState: SkillPublicState;
    // skill 完成后的 handoff（对齐 ClawGraph handoff 设计）
    handoff: SkillHandoff;
  };
  
  // 3. 生命周期（skill 不只是"被调用"，它有完整生命周期）
  lifecycle: {
    onLoad(): Promise<void>;        // 预热
    onActivate(context: SkillActivationContext): Promise<void>;
    execute(input: SkillInput): AsyncGenerator<SkillOutput>; // 流式输出
    onDeactivate(): Promise<void>;
    onError(error: Error): SkillRecoveryAction;
  };
  
  // 4. 组合接口（skill 可以调用其他 skill）
  composition: {
    // skill A 可以声明它需要 skill B 的能力
    // runtime 负责解析依赖、按顺序激活
    dependsOn?: string[];
    // skill 可以 fan-out 到多个子 skill
    canOrchestrate?: boolean;
  };
}

// Skill 调度器——runtime 核心组件
interface SkillScheduler {
  
  // 基于任务需求动态匹配 skill
  // 不是"用户选 skill"，而是"runtime 自动匹配"
  matchSkill(
    task: TaskDescription,
    roleContract: RoleContract,
    availableSkills: SkillManifest[]
  ): SkillMatchResult;
  
  // progressive disclosure：
  // 先暴露 skill 的摘要给模型
  // 模型认为需要时，再加载完整 skill 内容
  // 这解决了 skill 过多导致上下文膨胀的问题
  progressiveDisclose(
    skill: SkillRuntimeUnit,
    level: 'summary' | 'interface' | 'full'
  ): SkillDisclosure;
  
  // Skill 组合解析
  resolveComposition(
    primarySkill: SkillRuntimeUnit,
    availableSkills: SkillManifest[]
  ): CompositionPlan;
}
```

**Progressive Disclosure——解决 skill 过多的核心问题**：

Skill 相关工作已经从狭窄的函数调用和工具学习向可复用能力包、注册表和渐进式披露机制扩展。

```
当前问题：
136 个 skill → 全部 definition 塞进上下文 → token 爆炸

Progressive Disclosure 方案：
Level 0: Skill 名称列表（50 tokens）
Level 1: Skill 摘要（每个 ~20 tokens）
Level 2: Skill 接口（参数、返回值）
Level 3: Skill 完整内容（按需加载）

runtime 根据任务类型，自动决定暴露哪个 level
```

### 方向 4：事件驱动执行模型（替代轮询心跳）

你的 runtime 当前有心跳系统（`set-heartbeats`、`last-heartbeat`、`tick` 广播事件）。这是一个**轮询模型**的特征。

事件驱动架构允许 AI agent 立即对变化做出反应，而不是浪费资源轮询。

2025-2026 年，行业正在向事件驱动架构（EDA）收敛，作为 agent 系统的自然通信骨干。LangGraph 1.0 采用 Pregel/BSP 执行模型，状态更新即事件。AutoGen v0.4 从头基于 actor 模型重建，使用带类型的消息传递。Google 的 A2A 协议使用 Server-Sent Events 进行长期任务协调。

**你的 runtime 应该如何迁移**：

```typescript
// 当前模型（轮询/心跳驱动）：
//
// heartbeat tick（定时）
//   → 检查是否有待处理工作
//   → 如果有 → 触发执行
//
// 问题：tick 间隔内的事件需要等到下一次 tick 才被处理

// 目标模型（事件驱动）：
//
// 事件发生 → 立即路由到对应的 event handler
// agent 只在有事可做时消耗计算资源
//
// 关键事件类型：

type AgentEvent =
  // 代码变更事件（来自文件系统 watcher）
  | { type: 'fs:change'; path: string; change: FileChange }
  // 编译结果事件（来自增量编译器）
  | { type: 'compile:result'; success: boolean; errors: CompileError[] }
  // 外部触发事件（来自 channels/webhooks）
  | { type: 'channel:message'; source: string; content: Message }
  // 工具完成事件（工具执行完毕）
  | { type: 'tool:complete'; toolName: string; result: ToolResult }
  // 定时事件（替代心跳轮询）
  | { type: 'schedule:tick'; cronId: string }
  // 人类介入事件（来自审批/Guide/Queue）
  | { type: 'human:intervention'; mode: 'guide' | 'queue' | 'interrupt' }

// Mission Loop 的 tick 可以从"定时轮询"
// 改为"事件驱动唤醒"：
// - 子 agent 完成 → 触发 mission.tick
// - 外部依赖就绪 → 触发 mission.tick
// - 人类审批通过 → 触发 mission.tick
// 不再需要固定间隔的心跳
```

在生产环境中，正确的模式通常是：快路径事件、协调轮询、写边界处的幂等处理器，以及能在间隙中保持状态的持久运行时的组合。

### 方向 5：异构模型路由（Model Router）

你的系统已有 `model-catalog/` 和 `provider-runtime/`，以及 `effort` 七级映射。但这是**静态的**——角色契约里写死了 `model.default` 和 `model.fallback`。

真正的 runtime 层优化是**动态模型路由**：

运行时的 Mixture-of-Models 架构，带有动态专业知识 broker 和二次投票共识机制，使小型模型集成能够匹配前沿模型的性能。

双过程认知理论的应用：当规划子任务被识别为简单时，动态用较小的模型替换主干，从而减少单次推理时间。

**对你系统的具体实现**：

```typescript
// model-catalog/dynamic-router.ts
// 在已有的 provider-runtime 基础上增加动态决策层

interface DynamicModelRouter {
  
  // 核心判断：这个 tool call / 推理步骤需要多强的模型？
  selectModel(
    context: InferenceContext
  ): ModelSelection {
    
    const complexity = this.assessComplexity(context);
    
    switch (complexity) {
      
      // 简单路由/分类 → 快速小模型
      case 'trivial':
        return { model: 'gpt-4o-mini', reason: 'routing-only' };
      
      // 工具调用参数生成 → 中等模型
      case 'tool-call-gen':
        return { model: context.roleContract.model.default };
      
      // 复杂推理/代码生成 → 完整模型
      case 'deep-reasoning':
        return { 
          model: context.roleContract.model.default,
          thinking: 'high'  // 对齐已有的 effort 映射
        };
      
      // 验证/审计 → 可以用不同的模型（避免 self-evaluation bias）
      case 'verification':
        return {
          model: this.selectDifferentProvider(context.currentModel),
          reason: 'cross-model-verification'
        };
    }
  },
  
  // 实时负载感知路由
  routeByLoad(
    preferredModel: string,
    fallbacks: string[]
  ): string {
    // 检查当前 provider 的响应时间
    const latencies = this.providerMonitor.getLatencies();
    // 如果首选 provider 响应慢 → 自动切换
    return this.selectLowestLatency(preferredModel, fallbacks, latencies);
  }
}
```

**与已有 `effort` 系统的融合**：

```
已有：effort 级别 → thinking 级别（静态映射）
新增：runtime 复杂度评估 → 动态选择 effort + model

结果：
- 简单工具调用 → minimal effort + 小模型 → 省钱
- 代码生成 → high effort + 强模型 → 高质量
- 验证步骤 → 中等 effort + 不同 provider → 无偏估计
```

### 方向 6：Coding Agent 专有的 Diff-Aware 执行优化

这是专门针对你的核心场景（coding agent）的 runtime 优化，在通用 agent 框架中完全找不到对标。

**问题**：coding agent 最昂贵的工具调用是读文件。一个修改了 5 个文件的任务，每一轮推理都要重新把这些文件内容塞进上下文。

**解决方案**：Diff-Aware Context Injection

```typescript
// context-engine/diff-aware-injector.ts
// 只注入变化的部分，不是整个文件

interface DiffAwareContextInjector {
  
  // 维护文件内容的上一次快照
  fileSnapshots: Map<string, FileSnapshot>;
  
  // 当 agent 需要读文件时
  injectFileContext(
    filePath: string,
    agentContext: AgentContext
  ): FileContextInjection {
    
    const snapshot = this.fileSnapshots.get(filePath);
    
    // 第一次读：注入完整内容，记录快照
    if (!snapshot) {
      const content = fs.readFileSync(filePath, 'utf-8');
      this.fileSnapshots.set(filePath, { content, timestamp: Date.now() });
      return { mode: 'full', content };
    }
    
    // 再次读：只注入 diff
    const current = fs.readFileSync(filePath, 'utf-8');
    const diff = this.computeDiff(snapshot.content, current);
    
    if (diff.changeRatio < 0.3) {
      // 变化不足 30% → 只注入 diff
      return {
        mode: 'diff',
        diff,
        message: `[File changed since last read. Showing diff only:]`,
        // token 节省可观
      };
    } else {
      // 大幅变化 → 注入完整内容
      return { mode: 'full', content: current };
    }
  },
  
  // 与 ProjectMap 的集成：
  // 当项目地图更新时，只向 agent 注入变化的符号
  injectSymbolDelta(
    previousMapVersion: string,
    currentMapVersion: string
  ): SymbolDeltaInjection {
    const delta = this.projectMap.diffVersions(previousMapVersion, currentMapVersion);
    return {
      added: delta.newSymbols,
      modified: delta.changedSymbols,
      removed: delta.deletedSymbols,
      // 不重新注入整个项目地图
    };
  }
}
```

## 三、Skill 管理的去中心化设计

OpenClaw 的 skill 市场采用安装即运行的信任模型，没有正式审查、签名或能力声明要求。

这是你能实现真正差异化的地方——**建立去中心化的 skill 治理层**：

```typescript
// skills/decentralized-registry.ts

// 当前：中心化市场 → 单点信任 → 安装即运行
// 目标：去中心化注册 → 多方验证 → 能力声明

interface DecentralizedSkillRegistry {
  
  // === Skill 发布层 ===
  
  publish(skill: SkillPackage): PublishResult {
    // 1. 能力声明必须存在（不是可选的）
    this.requireCapabilityManifest(skill);
    
    // 2. 权限声明必须存在（我需要什么权限）
    this.requirePermissionDeclaration(skill);
    
    // 3. 签名（发布者身份）
    this.requireSignature(skill);
    
    // 存入注册表（本地优先，不依赖中心化服务）
    return this.localRegistry.store(skill);
  },
  
  // === Skill 发现层（Progressive Disclosure）===
  
  // 给模型看的：只有摘要
  discoverByTask(task: string): SkillSummary[] {
    return this.localRegistry.search(task)
      .map(s => s.summary);  // 不暴露完整内容
  },
  
  // 给 runtime 看的：完整能力声明
  resolveCapabilities(skillId: string): CapabilityManifest {
    return this.localRegistry.get(skillId).capabilities;
  },
  
  // === Skill 验证层 ===
  
  // 安装前：静态分析 skill 代码
  auditBeforeInstall(skill: SkillPackage): AuditReport {
    return {
      permissionCheck: this.checkDeclaredVsActualPermissions(skill),
      dependencyCheck: this.checkDependencies(skill),
      signatureCheck: this.verifySignature(skill),
      // 不需要联网，纯本地静态分析
    };
  },
  
  // 运行时：skill 执行在能力沙箱内
  executeInSandbox(
    skill: SkillRuntimeUnit,
    input: SkillInput,
    declaredPermissions: PermissionSet
  ): SandboxedExecution {
    // 只给 skill 它声明需要的权限
    // 不给完整 agent 权限（与已有 Hard Tool Enforcement 对齐）
    const sandbox = this.createSandbox(declaredPermissions);
    return sandbox.run(skill, input);
  }
}
```

Skill 外部化不应该被理解为静态指令文件的发布。它是一个协调过程，程序性专长被规范化、可被发现、选择性披露、绑定到可执行基底，并组合成更大的能力结构。重要的不只是 skill 能否被写下来，而是它能否可靠地作为一个与检索状态和协议化接口互操作的可用动作单元进入 agent 的运行时。

## 五、一个核心判断

这六个方向有一个共同的本质——**它们都是在改变 runtime 的执行策略，而不是加功能**：

| 方向 | 改变的是 | 对应 OS 类比 |
|------|---------|------------|
| 投机执行 | 工具调用的时序策略 | CPU 的 branch prediction |
| Context Engineering | 内存的分配和复用策略 | OS 的内存管理器 |
| Skill Runtime | 模块的加载和调度策略 | OS 的动态链接库 |
| 事件驱动 | 任务的唤醒机制 | OS 的中断 vs 轮询 |
| 动态模型路由 | 计算资源的分配策略 | OS 的进程调度器 |
| Diff-Aware | I/O 的增量传输策略 | 文件系统的 CoW |

你的系统现在在**编排层**（ClawGraph、Role-first、Mission Loop）已经是 OS 级别的设计。这六个方向是把同样的设计哲学下沉到**执行层**——让 runtime 本身变得更聪明，而不只是让 agent 的行为更聪明。

这就是从"套壳"到"真正的 runtime"的核心区别。
